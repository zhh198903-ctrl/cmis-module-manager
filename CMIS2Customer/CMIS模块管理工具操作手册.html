1. 产品简介

CMIS Module Manager 是一款用于调测和管理符合 CMIS（Common Management Interface Specification）标准的光模块的桌面工具。支持读取模块身份信息、实时监控光功率与温度、配置数据通道（DataPath）、执行环回 / PRBS 诊断，以及直接读写任意寄存器。

1.1 CMIS 5.4 支持情况（本版起）

本工具自 v2.3.0 起按 OIF CMIS 5.4（2026-05-21 发布）解码。 5.4 与 5.3 完全向后兼容——规范原文即写明"5.3 合规的模块也是 5.4 合规的"， 所以手上的 5.3 模块行为不变，界面上只是不会出现 5.4 才有的那几项。 界面中凡是 5.4 才引入的内容，名称后都带一个 5.4 徽标——字段名后如此，卡片标题后也如此。

⚠ 不可调谐的模块，调谐页以前会「凭空」列出一堆栅格（v2.66.0 修复）。
这是规范里一条很容易踩的规则：选一个模块没有的页，模块不会报错—— 它会把页号清零、改成给你 Page 00h。 而 Page 00h 的上半区是厂商名、料号、序列号这些 ASCII 文本。
调谐能力表在 Page 04h，只有 01h:155.6 说「发射端可调谐」时才存在。 工具此前不看这一位就去读，于是读回来的其实是厂商名那几个字节， 再按栅格位图解码——一块根本没有可调谐激光器的模块， 调谐页上会显示 「支持 6.25 / 12.5 / 25 / 50 / 150 GHz 五种栅格」， 以及一个「123.36 到 −163.28 dBm」的可编程功率范围 （上下限还是反的）。
现在先看 01h:155.6：这一位是 0 就根本不去读那一页， 页面直接说明该模块没有 Page 04h/12h。 写入侧一直是按这一位拦的，页校验和那部分也一直跳过 Page 04h—— 只有读取这一条漏了。
ℹ 激光器调谐页：同一个栅格，下拉框和悬停提示可能显示成两个名字（v2.65.0 修复）。
规范给每一个栅格编码都定了名字，包括 1111b——它的含义是 「不可用 / Not available」，是一个有意义的值，不是空档。
界面此前自己抄了一份栅格名字表，而那份抄到 1001b（300 GHz）就停了。 于是一条处于 1111b 的通道，悬停提示显示「Not available」， 同一行的下拉框却显示「15」——同一个寄存器，同一行上两个答案。
现在名字只由后端给一份，界面直接用； 规范未定义的那几个编码（1010b–1110b） 也统一用后端解出来的写法，不再各猜各的。
⚠ 「数据通道」页勾选 DP Deinit 时，勾中的通道和实际生效的通道可能对不上（v2.64.0 修复）。
CMIS 要求一条数据通道的所有通道必须整体操作（Table 8-78）， 所以勾一个格子会把同一条数据通道的其余格子一起勾上。
问题在于「哪几条通道算同一条数据通道」被算了两遍： 服务端在收到请求时按「相邻且应用相同」归组， 而界面自己按「应用宽度的整块对齐」又算了一遍—— 这是两套不同的算法，在大多数通道配置下结果并不一致。
后果是：界面上勾中的格子，和模块实际停掉的通道，可以是两批不同的通道。 举个本工具自带模块就能复现的例子： 通道 1–4 配 4 通道应用、5–12 配 8 通道应用、13–16 再配 4 通道应用， 这时点通道 5 的格子，界面勾的是 1–8，模块停的却是 5–12。
现在归组只由服务端算一次，界面直接用它——勾中的就是会停的。
⚠ 升级中途如果程序挂了，界面不会再说「已更新完成」（v2.63.2 修复）。
升级到最后，旧版本会主动退出让新文件顶上，所以页面那一刻连不上服务是 正常且预期的结束方式。
问题是：连不上也可能是程序在下载途中崩了。 此前这两种情况被当成同一种，于是下载到一半挂掉，页面照样显示 「已更新到 vX —— 新版本已经装好了」， 可实际上一个文件都没动；用户重新打开，还是原来那个版本， 而且屏幕上没有任何地方说明发生过什么。
现在会区分：只有走到「安装中」之后断开才算成功； 在「下载中」「校验中」断开会明确报错， 并说明当前版本原封未动、可以重试。
ℹ 换一块模块时，标志「历史」会重新开始计（v2.63.1 修复）。
CMIS 的标志是读一次就清掉的，所以工具会自己记一份「从上次清除以来出现过什么」—— 这份记录属于当时那块模块。
先前只有点断开才会清掉它；如果不断开、直接连另一块模块 （接口允许这么做，脚本和自动化也是这么切换的）， 上一块的记录会原样留着，「起算时间」也还停在上一块那会儿—— 于是新模块一连上，就显示它在插上之前就报过告警。
现在连接时和断开时一样会清空重新计。 想手动清零仍然用面板上的「清除标志历史」，那只清工具自己的记录， 不会往模块里写任何东西。
⚠ 监控项没有，对应的告警标志也不该显示成「正常」（v2.63.0 修复）。
上一条修的是读数，这一条修的是标志位。 规范里写得很直接：「有门限的监控项才有对应的告警标志、警告标志」， 而且这些标志的类型标的是 Adv.（需广告）， 不像模块状态变化那种标 Rqd.（必有）。
所以发送光功率、偏置电流、接收光功率这三项的共 12 个门限标志， 以及温度、电源电压的共 8 个模块级门限标志， 都是跟着监控项走的（01h:159-160）， 而不是跟着 01h:157-158——后者只管 Tx 故障、丢失信号、 CDR 失锁、自适应均衡失败这四类。
此前工具只用 01h:157-158 判断，于是那 20 个门限标志 在没有对应监控项的模块上被画成绿点—— 「这里一切正常」，可根本就没有在测。 现在它们显示 n/a，「监控」汇总列在三项全无时也显示 n/a； 模块有的那几项照常显示，是逐项判断的。
顺带：这类标志不会再进入「历史」记录， 也不会点亮顶部的告警提示——历史是会一直留在屏幕上的， 记错一次就要人工清一次。
⚠ 模块没有的监控项，不再当成读数显示（v2.62.0 修复）。
CMIS 把每一项监控都定义为可选——温度、电源电压、发送光功率、偏置电流、接收光功率—— 模块在 01h:159-160 里广告自己到底有哪几项。 没有的那一项，寄存器仍然存在，只是读出来是 0。
此前工具照单全收地把这个 0 显示出来，而 0 在这里不是「空白」，是很吓人的读数： 0.0000 V 是模块没通电，0.000 mA 是激光器灭了， 0 微瓦换算成 dBm 是量程底部——而且会被标成红色告警。 也就是说，工具在替一块根本没有这项监控的模块报一个它从没说过的故障。
现在这些位置显示「not implemented」并注明是哪一位广告的（如 01h:160.0）， 不参与告警配色。模块实现了的那些监控照常显示——这是逐项判断的， 不会因为缺一项就把整行藏掉。
⚠ 演示模块不会再自己「定时」报失锁了（v2.62.0 修复）。
此前第 8 条通道的 Tx CDR 失锁每 60 秒、Rx CDR 失锁每 75 秒自己亮一次再灭掉， 而那块模块的所有读数都是健康的。 一个按秒表闪的告警，会让人学会所有告警都不用看—— 这和之前修掉的「温度告警每 30 秒闪一次」是同一个毛病，只是漏了通道级的这两处。
更糟的是那一行是直接赋值而不是置位，所以它还会把真实读数刚刚触发的 Rx 失锁/丢失信号标志抹掉。
现在 Rx 的失锁与丢失信号只由接收光功率决定，健康的模块跑多久都是安静的。 （这两处只影响 Mock 演示，接真实模块时标志一直是模块自己给的。）
⚠ 「寄存器直读直写」页多了一个 Bank 输入框（v2.61.0）。
CMIS 里有一批页是按 Bank 分组的（10h–5Fh、60h–62h、 6Dh、9Fh、A0h–AFh）： 同一个页号 + 同一个地址，在不同 Bank 上是不同通道的寄存器， Bank b 对应第 8b+1 到 8b+8 条通道。
此前这个页面只能填页号和地址，读写永远落在 Bank 0—— 也就是说，通道数超过 8 的模块，第 9 条以后的寄存器根本够不着， 而且屏幕上没有任何地方说明你看的是哪个 Bank； 想写第 17 条通道的寄存器，实际会写到第 1 条上。
现在：填 Bank 即可读写对应的那一组通道，十六进制转储上方会写明 「Page 0x11 Bank 2 · lanes 17-24」； Bank 填超出模块实际 Bank 数、或填在不分 Bank 的页上（比如 01h、 02h）、或填在下半区（0x00–0x7F，本来就不分页也不分 Bank）， 都会直接报错，而不是默默给你 Bank 0 的内容。
只有 8 条通道的模块只有一个 Bank，这个框填 0 即可， 输入框下方也会写明当前页分不分 Bank、本模块有几个 Bank。
⚠ 通道数超过 8 的可调谐模块，调谐第 9 条及以后的通道现在才真正生效（v2.60.0 修复）。
激光器调谐用的 Page 12h 是按介质通道分 Bank 的，每个 Bank 装 8 条通道， 第 9 条和第 1 条在同一个地址上，靠 Bank 号区分。 此前写入时只认页号、不认 Bank：第 9 条及以后的调谐被悄悄丢掉， 界面却回「已写入」；如果同时改了第 1 条，那一条还会跟着第 9 条一起被改。
现在每次写入都会带上 Bank 号；通道号超出模块实际通道数会直接报错而不是被忽略。
另外：一次请求里只要有一条通道的参数非法，整个请求都不会写， 不会再出现「前几条改了、后几条没改，而且没人知道改到哪」的半截状态。 只有 8 条通道的模块不受这个问题影响。
ℹ 还支持这几种适配器（v2.59.0 起）：
CP2112（Silicon Labs）和 MCP2221 / MCP2221A（Microchip）—— 这两种是 HID 设备，Windows 用系统自带的驱动接管， 连驱动都不用装，插上就能在「适配器」里选到。
FTDI（FT232H / FT2232H）现在多了一条 ftd2xx 通道， 用 FTDI 官方驱动即可，不再需要 Zadig 替换驱动 （替换驱动会让机器上其它 FTDI 软件用不了，这也是原来那条 ftdi 通道的代价）。
顺带一提：只有 CH341 看不到「模块没应答」， 所以接 CH341 时连接会额外探一次总线（见下一条）。 CP2112 / MCP2221 / FTDI 能直接拿到应答位，没插模块时会当场报错。
ℹ CH341：安装驱动后 CH341DLL.dll 会自动注册到系统，EXE 无需额外配置， 开箱即用。
为什么本工具的 EXE 是 32 位：WCH 驱动包装进系统的 CH341DLL.dll 是 32 位的，而 64 位程序无法加载 32 位 DLL —— 这是 Windows 的限制，不是驱动或工具的问题。所以从 v2.58.0 起客户版 EXE 改为 32 位， 直接用驱动自带的那个 DLL，不需要你额外下载或放置任何文件。 （顺带：32 位包体积也小了约四成。）
⚠ 没插模块（或模块没插到位）时，工具会明确告诉你，而不是编一只出来。 空的 I2C 总线被上拉电阻拉高，每个字节都读回 0xFF； 而 CH341 的接口看不到缺失的 ACK，会把这次读当成成功返回。
v2.58.0 之前，工具就把这一串 FF 当数据解析了，界面上会出现一只 根本不存在的模块：CMIS 15.15、256 通道、 模块状态 Reserved、厂商名一串乱码、温度 -0.0039 °C。
现在连接时会先读低位内存前 3 个字节：全 FF 或全 00 就判定总线上没有模块应答，直接拒绝连接并说明读到了什么、该检查哪几项 （模块是否插到位、适配器的 I2C 线是否接对、地址是否为 0x50）。
⚠ CH347 注意：CH347SER.EXE 安装的是串口驱动（设备管理器可识别设备），但 I2C 通信所需的 CH347DLL.dll 可能不会自动安装到系统。若工具显示 CH347 unavailable，请从 WCH 官网下载 CH347EVT 开发资料包，找到 CH347DLL.dll，复制到 EXE 同目录或 System32 下。
⚠ 若设备管理器中设备图标有黄色感叹号，说明驱动安装不完整。请右键该设备 → 更新驱动程序，或重新运行安装程序。

本机端口:查看、修改,以及被占用时

程序只监听本机 127.0.0.1,默认端口 5000。

  • 查看和修改:点标题栏的 ⚙ Display,在 Server port 一栏能看到当前地址、 这个端口是怎么来的(默认 / 已保存 / 环境变量),输入新端口(1024–65535)后点 Save & switch port:服务器当场切到新端口,页面自动在新地址上重新打开, 主题、缩放、字体等显示设置会一起带过去。
  • 保存在哪:cmis_settings.json,和 EXE 放在同一个文件夹里; 下次启动直接用它。删掉这个文件就回到默认的 5000。
  • 默认端口被别的程序占用时:程序不会启动失败,而是先在系统分配的一个空闲端口上启动, 浏览器打开后弹出对话框,说明哪个端口被占用、原因是什么,请你手动输入以后要用的端口; 确定后保存并切换过去。点 Not now 则本次先用临时端口,之后随时可在 ⚙ Display 里修改。 控制台上也会打印同样的说明。
  • 占用端口的其实是本工具自己(比如双击了两次 EXE):不会弹窗, 第二个程序直接打开已在运行的那一个,然后退出。
  • 高级:设置环境变量 CMIS_PORT=5005 可临时指定端口,它优先于已保存的设置 (界面上会注明)。

为什么要这样:macOS 上的「隔空播放接收器」就占用 5000 端口;在 Windows 上, 服务器绑定端口时的方式允许与已经在监听的程序共用同一个端口, 结果浏览器连到哪一个由系统决定——你可能看到的是别的程序,甚至是一个 403 错误页。 现在启动时会先检测,被占用就明确告诉你。

5.2 检查并升级到最新版本

标题右侧版本徽章旁有 ↑ Update 按钮，点击即联网检查 GitHub 上是否有新版本：

  • 已是最新：提示「Already on the newest version」，按钮不变
  • 有新版本：按钮变为琥珀色的 ↑ v新版本号，弹出确认框显示版本号与下载大小。 确认后自动下载、校验并替换全部文件，当前程序随即退出。 多数情况下你什么都不用做：升级助手会把新版本拉起来，页面自己重新连上并刷新。 页面上的绿色对勾表示下载与校验已通过、文件替换正在进行，并给出 「Start CMIS_Module_Manager.exe again」作为兜底提示—— 若等待约一分钟后页面仍停在该提示，再双击一次 EXE 即可（不要在自动重启成功后再双击， 否则会多开一个实例）。整个过程记录在 EXE 同目录的 update.log 里
  • 无法联网：明确提示无法访问 GitHub，并给出手动下载地址。 不会把联网失败误报成"已是最新"。检查版本时若连接失败会自动重试 3 次再报错， 以免一次抖动就被当成 GitHub 不可达
  • 双下载源，哪个快用哪个：升级包同时放在 GitHub Release 和作者的下载站 （106.14.76.130）。点 Update 后工具会各测一次实际速度（约 10–40 秒， 取决于网络），然后从快的那个下载；下载中若该源失败，会自动切到另一个 并接着已下载的部分继续，不用重来。哪个源快因时因地而异，所以是每次实测而不是写死。
    版本号和校验值始终只从 GitHub 取（HTTPS）。下载站只提供文件本身， 它说不了"哪个是最新版"，也无法让一个包通过校验——即便下载站被篡改， 最坏的结果也只是升级失败，装不进坏包
  • 下载过程可见，界面不卡：按钮会实时显示进度（Updating… 58%）， 测速结束后还会提示这次是从哪个源下载的。下载期间界面照常可用， 可以继续看监控、读寄存器——下载在后台线程进行，不占用界面。 16 MB 在快网上几秒完成，在慢速链路上可能要几十分钟， 只要百分比还在涨就是正常的，不要以为程序卡死而去关掉它
  • 下载中断会自动续传：升级包约 16 MB，在慢速或走代理的网络上经常传到一半被掐断。 断开后工具会只请求尚未下到的那部分字节接着传，而不是从头再来。 只要还在往前推进就会一直重试下去，只有连续多次一个字节都没传成才会放弃—— 所以链路再差也能一点点攒完，不会出现"每次都差一点、永远下不完"。 对方服务器若不支持续传，则该次从头开始，不会把文件拼坏。
    已下载的部分在关掉程序后仍然保留：存放在 EXE 同目录的 _cmis_download 文件夹里，明天再点 Update 会接着上次的进度传。 切换到另一个版本时，旧版本残留的半成品会被自动清掉，不会长期占着磁盘
  • 校验不通过：下载包会逐字节比对 GitHub 公布的 SHA-256 摘要， 对不上就丢弃、不安装。如果该版本压根没有公布摘要，同样拒绝安装并提示你 自行到 Release 页面手动下载——"无法校验"和"校验失败"一样危险，不会放行。 续传也由这道校验兜底：万一拼接出错，整包摘要必然对不上，装不进去
⚠ 升级会关闭当前程序并重启。若正在连接模块做测量，请先 Disconnect 再升级。
自动重启不保证成功：程序要替换的是自己正在运行的那个文件， 升级助手会尝试两次并轮询新版本是否起来。绝大多数情况下会成功、页面自动回来； 失败时不会有任何损失，双击 EXE 即可，文件已经是新版本。 升级仅在 EXE 版可用；从源码运行时会提示改用 git pull。 本工具只在你点击该按钮时才联网，平时不会主动访问外部网络。
🔒 关于本机端口的安全性：程序只监听 127.0.0.1，外部机器无法访问。 自 v2.1.0 起，所有 /api/ 接口还会拒绝由其它网页发起的请求—— 你在浏览器里打开的任何站点，都无法借你的浏览器去连接模块、改寄存器或触发升级。 即便有人把自己的域名解析到你本机（DNS rebinding），接口同样会因 Host 不在白名单而被拒。
需要说清的一点：自 v2.2.0 起，界面页面本身和 css/js 等静态文件不设此限制， 从任何地方点链接打开 http://127.0.0.1:5000（或你设置的端口）都能正常显示界面—— 因为光是拿到页面并不能操作模块，所有能碰模块的入口都在 /api/ 下面。 可用的本机地址有三个：127.0.0.1、localhost、[::1]（带或不带当前端口号，默认 :5000）。
你自己写的脚本、curl、Python 程序不受此限制影响，但有两条硬要求： 带 body 的 POST 必须是 Content-Type: application/json，否则返回 415； 且必须用上面三个本机地址访问，用本机主机名会被拒。

5.3 数值进制的表示约定

寄存器工具里一个裸数字容易被误读，因此界面上所有数值都可判别进制：

进制写法出现位置
十六进制0x 前缀，如 0x83 寄存器地址、Interface ID、Raw 十六进制转储
二进制0b 前缀，如 0b00000101 位掩码，如 Applications 表的 Host Lane Assign
十进制无前缀，表头标注 dec 通道号、lane 数、带单位的监控值

表头的灰色小字会注明该列的进制与所属寄存器；悬停提示则同时给出三种进制，无需心算换算。

5.5 读取失败时各卡片的表现（务必了解）

只有 Monitoring 卡片会在读取失败时把数据置灰并显示过期横幅。其余所有卡片—— Squelch、Loopback、PRBS、Module Thresholds、DataPath、BER、SNR、Error/Bit Counters、 Module Control、Applications——失败时的表现是：

  • 右下角弹一条红色提示，3 秒后自动消失，之后没有任何痕迹
  • 卡片里的旧数值原样留着，没有任何标记——看上去和读取成功完全一样
⚠ 后果是：如果你没看见那 3 秒的提示，就会把上一次成功读取的旧值当作当前状态。 记录数据或判断故障前，请先点该卡片的 ↻ Refresh 并确认没有弹出红色提示。 提示条一律出现在窗口右下角，没有历史记录，错过就查不到了。

8. Monitoring — 实时监控

⚠ 模块不在 ModuleReady 时，这一页以前会报出根本不该被当真的告警。 规范把话说得很直接：模块级监控读数只有在 ModuleReady 状态下 才被要求满足精度指标；告警 / 警告标志的语义，也只在 ModuleReady 状态下有保证。
但模块在别的状态下照样会给你一个数。 以前监控接口只把这些数原样送上来，连模块当前状态都不带—— 状态在另一个接口里，而这张表从来不去看它。 于是把模块切到低功耗（ModuleLowPwr）之后， Tx 光功率读回 -40 dBm，表格就按低告警标成红色： 一块只是睡着了的模块，被界面说成故障。
现在：监控接口每次轮询都带上模块状态； 不在 ModuleReady 时，表格顶部会写明当前是哪个状态、以及为什么这些数不作数， 数值照常显示（模块确实这么答的，看着模块下电的人需要看到它）， 但不再上告警配色——颜色才是那个「下结论」的动作。 概要行里按额定温度范围给温度上色，同样只在 ModuleReady 时才做。 回到 ModuleReady 后一切照旧。
⚠ 同一条规矩还有逐通道的那一半：把某条数据通道停掉，这条通道就会被画成「告警」。 规范对数据通道相关的监控另有一句：它们的告警 / 警告标志， 只在 DPInitialized 和 DPActivated 两个状态下有保证—— 七个状态里就这两个。
可通道停掉之后，模块照样报一个光功率： 用本工具的 DPDeinit 把通道拉下来，受影响的每条通道立刻读回 -40 dBm，表格就按低告警标成红色。 而这期间模块本身一直是 ModuleReady， 所以上一条（模块级）的判断不会触发，也不该触发—— 那是另一个范围的另一条规矩。结果就是：你自己刚关掉的通道， 界面回头告诉你它坏了。
现在每条通道单独判断：模块在 ModuleReady 且本通道的数据通道处于 DPInitialized / DPActivated， 两个条件都满足才上告警配色。不满足时该通道的 Tx 光功率、Tx 偏置、Rx 光功率三格转为淡色， 悬停提示里写明本通道当前是哪个状态、以及为什么这些数不作数。 数值照常显示。通道重新起来后一切照旧。

Lane Flags 为什么会"自己消失"——闩锁与读清

这是 CMIS 排障时最容易踩的一条，与工具无关，是规范的设计：

⚠ CMIS 5.4 规定 Flag 是闩锁位，读取包含它的那个字节就会把它清零 （原文："a Flag bit remains set (latched) until cleared by a READ of the Byte containing the Flag"）。
这意味着：一次瞬时故障（光纤没插紧、电源抖动、对端重启）会把 Flag 置位， 模块一直保持到有人来读——而读到它的那一次刷新，也就把它擦掉了。 界面每 2 秒刷新一次，所以这个事件只会在某一帧里出现，看漏了就再也查不到。 这不是模块或工具出错，是 Flag 的定义如此。

因此记住它是主机的责任，本工具替你记：Lane Flags 表里，某个 Flag 曾经触发过、 但现在已经恢复的通道，会保留一个 ●! 标记，与"从未触发"（●） 区分开。点Clear flag history 清空这份记录、从当下重新开始计。 换模块或重新连接也会自动清空。

DP Changed —— 数据通道弹过的唯一证据

Lane Flags 表第一列是 DP Changed（11h:134）。按 CMIS 6.3.3， 模块在数据通道经过真实过渡后进入稳定态时置位这一位——换句话说， 它是模块自己记下的"这条通道掉下去又回来了"。

⚠ 链路弹一次之后，状态在前后两次刷新里都是 Activated， 光看状态列什么也看不出来。DP Changed 是唯一的线索。
它同样是 Flag——闩锁、读清——所以和其它标志一样，恢复后会保留 ●! 标记。模块复位后所有通道都会置位， 因为每条通道都重新走了一遍 DPInit，这是正常的。

Output —— 输出到底通没通

Monitoring 表新增一列 Output，分两行显示 Tx 和 Rx， 读的是 11h:132（OutputStatusRx）和 11h:133（OutputStatusTx）。 CMIS 5.4 Table 8-95 把这两个字节定为只读、必需： 1 表示该路输出信号有效，0 表示被静音或无效。

⚠ 它与数据通道状态无关。规范 8.14.2 写明输出状态 “independent of the state of the DPSM instances”——本工具里四个控制都能把输出静音， 而都不会改变 DataPath State：
① DataPath 页的 Tx Enable（10h:130 OutputDisableTx）
② Squelch 页的 Force Squelch Tx（10h:132）
③ Squelch 页的 Rx Output Disable（10h:138）
④ 模块自己的自动静音（丢失输入时）
以前勾上这些框之后，界面上唯一的变化就是那个框被勾上了； 状态列依旧是绿色的 Activated。现在 Output 列会变成 ○，鼠标悬停会说明该去查哪个开关。

Lane Flags 表同时新增一列 Rx Output（11h:153）。 按 8.14.2，只有 Rx 侧有这个变化标志（闩锁、读清）， 因为只有 Rx 输出的通断会让主机采取动作；Tx 侧规范明确说不定义。

ℹ 两次刷新之间静音一下又恢复的情况，11h:132 本身看不出来； 这个 Flag 是唯一的记录，和其它标志一样会保留 ●! 历史标记。

停用一条数据通道（DP Deinit）

DataPath Config 表里的 DP Deinit 那一列以前只是个显示（Deinit / Active）， 点不动。而 10h:128（Table 8-78）按规范是 可读写、必需的，它是唯一能主动停用一条数据通道的手段。

ℹ 和 Tx Enable 不是一回事：取消 Tx Enable 只是把输出静音， 数据通道仍处于 Activated；DP Deinit 才是真的把这条通道停下来。

现在它是复选框。按 Table 8-78，一条 Data Path 的所有通道必须取相同值， 所以勾一个会自动带上同条通道的其余几路——在你按 Apply 之前就看得到 会发生什么。两条通道互不影响：停用后四路时，前四路照常运行。

ℹ 放开时通道会重新走一遍 DPInit 回来，因此会留下 ●! 标记（DP Changed）——与其它重新初始化 留下的证据一致。被停用的通道不会被 Apply 抬起来， 要恢复必须先取消勾选。
另：规范规定模块只在 ModuleReady 状态下评估这个字节， 所以主机可以在低功耗状态下先把全部位置上，阻止数据通道自动启动。

接口写入：只改你写了的，写错名字会报错

这一节只关系到直接调 REST 接口的人（写脚本、或让 Claude Code 驱动工具）。界面操作不受影响，因为它每次都把全部字段一起发。

⚠ 以前的行为：没提到的字段默认为 0。于是只设一个控制， 会把其余的静默地清掉，而且返回“成功”。
最危险的一处在数据通道接口：app_select 不提及就默认 全部为 1——只发一个极性改动，会把每一路的 Application 重配成 1。

被拒绝的请求，不会已经改掉一半

PRBS 一次请求里有四个引擎（主机/媒体侧的产生器和检测器）。它此前是校验一个、写一个：如果第四个引擎的参数非法，前三个已经写进模块了，然后才返回错误。

⚠ 看到报错的人——不管是操作员还是脚本——很自然会认为什么都没发生。而实际上主机侧产生器已经被重新配置了。
界面每次 Apply 都会把四个引擎一起发出去，所以只要给其中一个选了模块不支持的码型，就会踩到。

这条规矩激光器调谐接口一直就有（代码里写着「所有写入先算好并校验完，再一起下发」），只是没推广到 PRBS。现在 PRBS 也是：先把四个引擎全部算好校验完，再统一下发；任何一个不合法，一个字节都不写。

现在所有写入接口统一为：

  • 没提到的字段保持原值（先读后写）
  • 无法识别的字段返回 400，并列出该接口接受哪些字段
  • 一次请求要么全写、要么一个字节都不写——先把所有要写的内容算好并校验完，再统一下发
⚠ 这条规矩当初只落实到那四个接口，另外三个漏了——而漏掉的恰好是后果最重的：
· PRBS：只改使能掩码、不提 patterns，每一条通道的码型都被悄悄改成 0 号（PRBS31Q），反相 / 字节交换 / FEC 位置掩码一起清零，然后回复「成功」。
· 激光器调谐：字段名拼错（target_power 少了 _dbm）被静默丢弃，通道号照改、发射功率没动，回复却是「参数已写入」。
· 通道交换：enable 拼成 enabled 直接被忽略，回复「成功」，什么也没切换。
界面每次 Apply 都会把全部字段发出去，所以点界面碰不到；这是走 API 时才会踩的。
ℹ 模块控制寄存器还有一个读写不一致的问题： 读回来叫 low_pwr_request_sw，写进去只认 low_pwr—— 五个控制里四个如此。把读到的状态原样写回去，四个控制都静默无效。 现在两种写法都接受。

❗ Apply 只重启你改过的那条数据通道

按 CMIS 6.2.3.3.1，Apply 必须对该 Data Path 的所有通道同时触发—— 是那一条通道，不是整个模块。工具以前每次都写 0xFF。

⚠ 后果：一个模块上跑着两个 400G 口时（比如 2× 400GBASE-FR4）， 你只改了后四路的配置，前四路也会一起断—— 那个口你根本没碰过。
现在只对暂存配置真正发生变化的那几条 Data Path 触发。

分组依据是 Application 声明的主机通道宽度： 一个占 4 条通道的 Application，1–4 路和 5–8 路就是两条独立的 Data Path。 接口返回里多了一个 applied_lanes，写明这次到底重启了哪几路。

ℹ 什么情况下仍然全部重启：你什么都没改就点 Apply。 那是一个明确的“重新调试一遍”请求，静默地什么都不做等于拿掉这个能力。 只有能定位改动时才收窄。
ℹ 有些改动压根不需要 Apply：Page 10h 的 129–142 按规范是“独立于数据通道状态机或控制集”的直接控制： 极性翻转、Tx 关断、静默写下去就生效。 以前只翻一下极性再点 Apply，会为一个本来不需要 Apply 的改动 重启全部数据通道。
⚠ 有两种情况，模块会把 Apply 悄悄丢掉——工具以前照样回报「成功」。 规范写得很清楚：
一、数据通道正处在过渡状态（DPInit / DPDeinit / DPTxTurnOn / DPTxTurnOff）时收到的 Apply， 模块直接忽略（这条针对支持免中断重配置的模块）；
二、ApplyImmediate 在 DPInitialized / DPActivated 之外的任何状态都会被忽略。
以前工具只挡住了第二条里「模块根本不支持免中断重配置」那半边， 两个状态条件都没查：把通道停掉之后马上点 Apply， 工具会返回成功，还会列出它「已经配置好」的是哪几条通道—— 而模块其实什么都没做。 「悄悄丢掉」是操作员唯一分辨不出来的失败： 你会以为这条链路已经在跑新配置了。
现在这两种情况都会被拒绝，并明确写出是哪条通道、当前在哪个状态， 例如「Lane 1 (Deactivated) 不在这两个状态里，请改用 Apply」。 仍然允许的是：停通道和 Apply 写在同一次请求里 （这正是规范规定的释放序列），以及在 DPDeactivated 上用 Apply（规范推荐的正是这个用法）。 只支持分步重配置的模块行为不变。
这类拒绝信息现在会在界面上停留 12 秒——原来的 3 秒不够把通道号读完。
⚠ 模块不在 ModuleReady 时，DataPath 的这些操作本来就不会生效——以前同样回报「成功」。 规范两句话叠在一起：DPDeinit 这个字节，模块只在 ModuleReady 状态下才会去读； 而且数据通道的状态机在模块进入 ModuleReady 之前，一直停在 DPDeactivated。
也就是说，在低功耗（ModuleLowPwr）下：DPDeinit 不被读取， 任何 Apply 都无法让数据通道离开 DPDeactivated。 工具以前照写不误、照报成功—— 等于说「模块在睡着的时候把自己重新配置好了」。
现在这三个操作（DPDeinit、Apply、ApplyImmediate） 在非 ModuleReady 状态下会被拒绝，并写明模块当前在哪个状态。
但拒绝是有选择的：规范把 10h:129–142 这几个逐通道控制 （极性翻转、输出关断、Squelch）明确列为 「与数据通道状态机和控制集无关」，而且写入即生效—— 所以它们在低功耗下照常可用，不会被这条拦下。 暂存 AppSelect 也一样：那只是写内存，状态机要等到 Apply 才会看它。
模块回到高功耗后，一切照旧。
⚠ 点「进入低功耗」之后，面板以前显示的是按下之前那个状态。 模块在 01h:167 里自己声明了两个上电 / 下电过渡最长要多久， 本工具内置的分页演示模块，全都声明「下电最长 1–5 秒」。 可工具写完控制字节只等了 50 毫秒，页面再过 200 毫秒 就去读状态—— 对任何真按自己声明的时间来走的模块，这时读回来的还是按下之前的状态， 却被当作这次操作的结果显示出来。 于是：提示条是绿的（「已请求低功耗」），状态栏还写着 ModuleReady， 操作员自然会再点一次。
现在按模块自己声明的时间等，不再用工具里写死的数字： 状态一到就立刻返回（不会白等满 5 秒）， 真等满了还没到，会明确提示模块现在在哪个状态、 以及这是按哪个声明（01h:167）等的。
软复位不宣称目标状态：它要先走 MgmtInit， 最后停在低功耗还是 ModuleReady，取决于它回来时那两个低功耗请求位—— 所以只等到「状态不再变化」为止。
模块没声明这个时间时，退回到原来的等待时长。
演示模块是瞬间切换的，所以这个问题在演示里看不出来—— 它只在按自己声明的时间走的真实模块上出现。
⚠ 同一类问题在媒体通道交换这里更糟：提交还在执行，面板却叫你「再按一次提交」。 模块在 6Dh:128 里声明了一次提交最长要多久， 工具本来就把这个值读出来并显示了，然后转头等自己写死的 100 毫秒。
对声明时间更长的模块，这时读回来的结果是 2：命令正在执行中——工具也正确解码成「进行中」， 可表格下面那行提示只看「生效了没有」，于是照样写着 「暂存的映射尚未生效 —— 请点提交」。 模块明明说了「我正在做」，界面却叫你把正在执行的命令再下一遍。
现在两件事都改了：按模块声明的时间等（而且做完就立刻返回， 不会白等满声明的上限——演示模块上这一步从 100 毫秒降到约 10 毫秒）， 并且把「正在执行」和「根本没提交」分成两条不同的提示：
■ 提交仍在执行；本模块声明最长 10-50 ms（6Dh:128）
■ 暂存的映射尚未生效 —— 请点提交
另外，被拒绝（结果码 3–6）不会被当成「正在执行」—— 否则你会一直等一件早就失败了的事。
ℹ 演示模块现在会像真模块一样「换页要等」。 规范规定：写完选页寄存器之后，模块最多要 10 ms （或它在 01h:169 里声明的那一小部分）才会用新页回答； 等不够就会读回上一页的内容——这正是本工具最看重的一条时序规则， 漏了它的表现是时有时无的数据错乱，很难查。
以前演示模块是立刻换页的，所以它分辨不出「守规矩的上位机」和 「不守规矩的上位机」：真把那个等待删掉，演示里也一切正常。 现在演示模块换页后会先继续回答上一页，直到它声明的时间到了为止。
这不改变你使用工具的方式（工具一直是按规矩等的）， 但它让这条规则真正被验证了：把等待去掉，测试会立刻大面积失败。 下位内存不受影响（它本来就不分页）， 重复选中同一页也不会重新计时。
⚠ 修复：参考时钟丢失的提示，以前只出现一次就消失了。 14h:132.7 是锁存 + 读后自清的标志： 读一次就没了。它带出来的那句提示说的是—— 用参考时钟的发生器 / 检测器「在它恢复之前都不能当真」。 可这条提示以前只看当前这次读到没读到， 于是刷新一次就不见了， 看上去像是参考时钟已经回来了——而模块从没这么说过。 丢失期间产出和校验的数据，在标志被清掉之后依然是可疑的。
现在它和这一页上另外四个锁存标志一样被记住： 当前正丢失时还是原来那句警告； 只是历史上出现过时，改用淡色显示并写明 「这是发生过的记录，不是实时读数」， 点清除标志历史后消失。
顺带把演示模块也修对了：规范里 14h:132–139 整段都是「锁存 + 读后自清」， 而演示模块只对其中两个字节这么做—— 另外五个（参考时钟、两个发生器失锁、两个门控完成）读完还在。 这意味着「工具有没有把这些标志记住」以前根本没被验证过。

Signal Integrity：Apply 一并提交的另一半

点 Apply 提交的是整个 Staged Control Set， 而工具以前只读其中的 AppSelect 和几个掩码。 它的另一半是信号完整性（SI）控制，在 Page 10h 的 153–173（Table 8-83 / 8-84）：自适应 Tx 均衡、主机控制的均衡目标值、 Rx CDR 旁路、Rx 输出均衡的前/后游标、Rx 输出幅度。

⚠ 以前这些既不读也不显示，于是工具每次 Apply 都在提交一组它自己也说不出名字的设置。更麻烦的是： ConfigRejectedInvalidSI（5h）本就是一个合法的拒绝理由， 工具也会把它显示出来——但它指向的值在界面上无处可查。
⚠ 超过 8 条通道的模块，这张表以前只有前 8 行。 Page 10h（暂存区）和 Page 11h（生效区）都是按 bank 分组的， 每个 bank 8 条通道；表里这六项全是逐通道的字段—— 自适应 Tx 均衡和 Rx CDR 是每条通道 1 个 bit， 另外四项是每条通道 4 个 bit（4 个字节装 8 条通道）。 也就是说，第 9 条通道起的设置在下一个 bank 的同一批地址上， 而工具这十二处读取全都停在 bank 0。
表格的行数是按读回来的长度铺的，所以结果不是报错，而是 DataPath 页列着 16 条通道、Signal Integrity 表却只有 8 行—— 正好在通道多到需要逐条看均衡设置的模块上， ConfigRejectedInvalidSI（5h）指向的那半边 后 8 条通道无处可查。
现在十二处都逐 bank 读。8 通道模块只有一个 bank， 行为和以前完全一样。

DataPath Config 页现在多了一张 Signal Integrity 表，逐通道列出这些值。 列是动态的——只列出 01h:161–162（Table 8-54）声明支持的那几项， 表尾写出模块声明的上限（01h:153–154）。 目前是只读的：先解决“看不到”，修改交给后续。

ℹ 两个容易读错的地方：
一是 Rx CDR 列的“Bypassed”不等于“关闭了某个开关”—— CDREnableRx 清零的含义是该通道的 CDR 被旁路，信号不再被重定时。
二是当模块只声明前游标控制时，按规范（Table 8-84） 后游标那几个字节里装的是前游标目标值—— 照地址直接叫它“post-cursor”就错了。遇到这种模块表上会先提醒。
ℹ 演示模块之前 Page 10h 的这一段是空的，读出来全 0—— 那意味着每一路 Rx CDR 都被旁路，而它同时声明自己有 CDR。 现已给出合理默认值。内置的 mock_sr8 故意 SI 能力较弱 （无主机控制 Tx 均衡目标、只有前游标），方便看到列变少的效果。

Rx 光功率读数是 OMA 还是平均功率

01h:151.4（Table 8-50）决定 Rx 光功率监控报的是 OMA（光调制幅度）还是平均功率。 这是两个不同的物理量，在调制信号上相差好几个 dB， 而接收灵敏度限值在规范里是按其中一个写的。

⚠ 以前 Rx Power 列只给一个 dBm 数，没说它是哪一个—— 拿它去对规范限值，对错了自己也不知道。 现在列头直接标出 · OMA 或 · Average power， 鼠标悬停给出寄存器位。

同一个字节里还有几位值得知道：151.7 探测器是 PIN 还是 APD；151.3 Rx LOS 响应的是 OMA 还是 Pav（与上面那位独立）； 151.2 / 151.1 是 Rx LOS 和 Tx 关断的快速模式时序。

❗ 有些模块的 Tx Enable 不是逐通道的

01h:151.0（TxDisableIsModuleWide）置位时， 任何一路的 OutputDisableTx 会关掉全部 Tx 输出。

⚠ 而 DataPath Config 页给的是 8 个看上去相互独立的复选框—— 它们说的正好相反。在跑着的链路上，取消勾选第 3 路的代价是 另外七路一起断。
现在这类模块上，勾任意一个框会八个一起动（和模块实际行为一致）， 表格上方也会先写明这件事。逐通道的模块不受影响。
ℹ 内置的 mock_fr4x2 故意声明为模块级 Tx 关断， 方便你在没有硬件时看到这个行为。

Aux1–3：同一个寄存器，意义由一个位决定

下部内存 18–23 是三个普通的 S16 寄存器， 但它们到底测的是什么，由 01h:145（Table 8-50）里的三个位决定：

寄存器位 = 0位 = 1
Aux1 Lower 18–19 自定义（厂商定义，无通用单位） TEC 电流
Aux2 Lower 20–21 激光器温度（1/256 °C） TEC 电流
Aux3 Lower 22–23 激光器温度（1/256 °C） 附加电源电压（100 µV）
⚠ 不读 01h:145 就拿这三个数，它们既没有单位也没有含义—— Aux2 的同一个数可能是摄氏度，也可能是 TEC 电流百分比。 工具此前把它们原样返回、界面一个都不显示， 于是制冷模块的激光器温度和 TEC 电流就白白扔了。

现在 Module Info 里按声明的含义逐行列出，带各自的单位。 TEC 电流是有符号百分比（占模块最大 TEC 电流幅度的比例）： 正值是加热，负值是制冷。规范里没有任何寄存器给出那个最大值， 所以无法诚实地换算成安培，工具也不会自己编一个。

ℹ 01h:159.4-2 声明这三个监控到底存不存在。 不存在就一行也不显示，而不是显示三个 0—— 0 °C 和“TEC 没在工作”都是看上去很合理的读数。 非制冷模块（内置的 DR8 / SR8 / FR4）本来就没有； 两个相干演示模块是制冷的，三项都有。

写入之后,模块可以暂时不应答

规范 Table 10-4:一次 WRITE 之后,模块可以在最长 10 ms(tWRITE,总线上叫 tNACK)内拒绝接下来的任何读写;写非易失存储器(Page 03h 用户 EEPROM,规范 8.7)之后最长 80 ms。5.2.3 给主机的办法是:按最坏时序等待、被拒后重试,或先探测模块是否就绪。

⚠ 工具三样都没做:所有适配器把「模块没应答」报成错误,工具直接当作失败返回。于是在写入后会短暂不应答的模块上,DataPath、Squelch、Loopback、PRBS 的 Apply 都会报错,Raw Registers 写完也读不回来。上一版把长写入拆成连续几次写入之后,第二段更容易落进第一段的拒绝期。

现在每次写入之后,工具会在规范允许的拒绝期内(一般 10 ms,Page 03h 为 80 ms)对被拒的读写自动重试;超过这个时限仍被拒,才作为真正的错误报告——不会无限等下去。没有写入在先时,被拒就是被拒,不重试。

会变的多字节量,一个一个读

规范 5.2.5.1:用和寄存器同样长的一次 READ 读一个多字节只读标量,模块保证读到的是同一时刻的值——「这条尤其适用于任何 2、4、8 字节的状态或监控寄存器」。而「对多个寄存器或寄存器数组的 READ 不保证一致」。

工具显示的会变的多字节量,之前都是整块读的:

  • 通道监控(Tx 光功率、偏置、Rx 光功率,Page 11h,每个 U16)
  • 诊断窗口(Page 14h:192–255):BER、SNR、误码与总比特计数——支持整页读的模块上是一次 64 字节
  • 实测激光频率(Page 12h,每个 U32)、采集计数器(Page 61h)、数据通路时延(Page 15h)
⚠ 模块在一次 READ 进行中更新数值时,整块读出的某个值可能高字节是上一次采样、低字节是下一次采样,差出 256 个计数——看起来就是一个正常读数。模块级监控(温度、Vcc、Aux)早就是逐个读的,其它都不是。

现在这些量都按各自的长度逐个读取:U16 读 2 字节,U32 读 4 字节,计数器(U64)读 8 字节。代价是读寄存器的次数变多,刷新会略慢一点。Raw Registers 仍按你给的长度读取——在监控区整块读时,单个值同样不保证一致。

一次 WRITE 最多 8 字节

规范 5.2.2.2:「一次成功的 WRITE 写入最多 8 个字节」;更长的只有第 8 章明确允许的地方才行。被拒绝的 WRITE「对模块没有任何作用」。

读取早就按这个上限分块了,写入却没有。两处会一次写超过 8 字节:

  • PRBS 用户码型(13h:224–255,最长 32 字节;Table 8-134 并没有放宽)
  • Raw Registers 写入(可以一直写到页尾)
⚠ 没有哪个适配器会按 8 字节切:CH341 整段一次发出,CP2112 和 MCP2221 按 60 字节左右切——那是它们自己的包长,不是模块的上限。守规矩的模块可以拒绝这次写入,而面板照样说「已写入」。

现在超过 8 字节的写入会拆成多次、每次最多 8 字节;Raw Registers 写完会注明分了几次(规范 5.2.5.2:多字节写入本来就不保证是一次整体写入)。刚好 8 字节的写入(比如一个 PRBS 引擎块、8 个 AppSel 字节)照旧一次写完。

唯一的例外是 Page 9Fh 的 CDB 消息头:写到 9Fh:129 就会发出 CDB 命令(规范 7.2.3),拆开写会让命令在消息头还没写完时就发出。所以超过 8 字节、又包含字节 129 的写入会被拒绝,并提示先写其余部分、最后写含 129 的那段。

内置模拟模块现在也会拒绝超过 8 字节的 WRITE,于是整套测试就成了一次全面检查:其它所有写入口都没有超过这个上限。

13h:177.7 作用到哪里:「被忽略」只在门控测量时成立

13h:177.7 StartStopIsGlobal(Table 8-127)置 1 时,在一个 Bank 上写启停控制——177.5 的复位、160 / 168 的检测器使能——等同于在所有 Bank 上同时写。

Table 8-129 给了一个例外:门控测量、并且模块只有一个全局 gate 定时器(13h:129.3 = 0)时,这个位被忽略。测量窗口那一行把这个例外当成了整条规则:只要 129.3 = 0 就说「被忽略」,不门控时也这么说。而不门控的情况归 Table 8-128 管,那里 177.7 = 1 有专门的一行:切换 177.5 会复位「所有 Bank 的所有通道」。

⚠ 于是在不门控、只有全局定时器的多 Bank 模块上,页面说这一位无效,而它其实让每一次启停都作用到所有 Bank。另外,勾选检测器使能是在 PRBS Checker 卡片上,那里对此一个字都没有:这一位生效时,勾 lane 1 会连带启动 lane 9、17。

现在:

  • 这一位作用到哪里由服务端统一判断,BER、Counters、PRBS 三张卡片用同一个结论:只有门控测量 + 全局定时器时说「被忽略」(标注 Table 8-129);其余情况说「作用于所有 Bank」。模块不做门控(13h:129.7-6 = 00b)时按不门控处理。
  • 该位为 0,或模块只有一个 Bank(无处可去)时,什么都不说。
  • PRBS Checker 卡片顶部会写明哪些通道一起启停,例如 24 通道模块上「lanes 1, 9, 17 start and stop together」。

这一节规范带着编辑注释「应改写以更清楚」,Table 8-130 里还有「因为 129.3 = 0 所以被忽略」这种与表名矛盾的行。工具只采用规范说得明确的部分,不自己补全。

Bank 广播:每一个按 Bank 写入的地方都要检查

Table 8-11:Lower 0x1A[7] BankBroadcastEnable 置 1 时,对通道分 Bank 的页上任何控制寄存器的写入,都会同时写进所有 Bank。

工具早先给 DataPath 和 Squelch 的写入加了这项检查,后来媒体通道切换也加了。另外四个同样逐 Bank 写入的地方却没有:

  • Loopback 和 PRBS(Page 13h)
  • 激光调谐(Page 12h,按媒体通道分 Bank,规范 8.15)
  • 采集计数器清零(Page 60h,「每个 Bank 对应 8 条通道」,规范 8.30)
⚠ 它们一个 Bank 接一个 Bank 地写。开了广播,每一次写都落到全部 Bank,最后一个 Bank 的值盖掉前面所有:在 24 通道模块上只开 lane 1–4 的 PRBS,结果一条都没开;清零 lane 1 和 3,lane 9、11、17、19 也被清掉;只调媒体通道 3 的激光,媒体通道 11 也跟着变——每一次都报告成功。

现在这四处也会拒绝各 Bank 不一致的请求,说明是哪一项,原配置不动;各 Bank 取同一个值时照常写入。激光调谐会指出会被连带改动的媒体通道,例如 setting the channel of media lane 3 would set it on media lane 11 too。PRBS 检查的是每个 Bank 实际要写的整块内容,包括请求里没提、沿用原值的字段。

规则属于写入方式,不属于最先发现它的那个面板:凡是选 Bank 再写的地方都要问这一句。

媒体侧环回与媒体侧 PRBS,同样按媒体通道

上一版把「按媒体通道」这条规则教给了 Page 10h 的通道控制。Page 13h 上有同一类控制,却被漏掉了:

  • 媒体侧环回(MediaSideOutputLoopbackEnable / MediaSideInputLoopbackEnable,Table 8-131)环回的是媒体通道——Figure 8-2 的示意图上就写着「只画出一条媒体通道」。
  • 媒体侧 PRBS 发生器与检测器(Table 8-121 / 8-125)按媒体通道运行:规范 8.16.11.1 说的是逐个切换「媒体(13h:168)通道的检测器使能位」,Table 8-138 也把它们的失锁标志记为「按媒体通道」。
⚠ 两个面板都按主机通道排行。在相干模块上(8 条主机通道、1 条媒体通道),每一行媒体侧里有 7 个勾选框控制的是模块不存在的通道:勾上就在一条不存在的通道上开了发生器,写入照样报告成功。PRBS 表随后还把那条通道的失锁历史显示成「从未失锁」——那是对一条不存在的通道所作的报告。

现在:

  • 媒体侧环回的两行、媒体侧发生器和检测器的整行(En / Invert / ByteSwap / FEC / Pattern),在模块没有的媒体通道上置灰,悬停说明依据 00h:210 和对应的表;置灰但保留原值。
  • 对不存在媒体通道的使能位做改动会被拒绝并说明原因;原值不变照常放行。只判使能位:它才是让东西跑起来的那一位,而页面回写的 FEC 位置对所有通道只有一个合法值。
  • 不支持逐通道环回的模块不受影响:规范规定那种模块上任何一位都代表全部通道,那一位并不指向哪条通道。
  • 失锁历史:不存在的媒体通道显示 n/a,接口里为 null。主机侧照旧。

规则属于寄存器家族:凡是按媒体通道索引的控制,都要问一句「这条媒体通道在不在」。

Tx 输出与 Tx 静噪的开关,也是按媒体通道的

Table 8-79 把 Page 10h 上的三项通道控制定义为按媒体通道:OutputDisableTx(「媒体通道 <i> 的 Tx 输出禁用」)、AutoSquelchDisableTx 和 OutputSquelchForceTx。

写这三项的两个面板——DataPath 表的 TX Enable 列、Squelch 表的两行 Tx——都按主机通道排行,也没有说明索引的其实是另一侧。

⚠ 在相干模块上(8 条主机通道、1 条媒体通道),这些行里有 7 个勾选框控制的是模块不存在的通道:勾上就写下一个无处生效的位,而写入照样报告成功。

现在:

  • 这些格子置灰,悬停说明依据 00h:210 和 Table 8-79;置灰但保留原值——页面整字节回写,清掉反而成了一次改动。
  • 对不存在媒体通道的那一位做改动会被拒绝并说明原因;原值不变照常放行。
  • 表头标明 media lane。两行 Rx(主机侧)不受影响。
  • 模块级 Tx 禁用(01h:151.0)同步勾选时,跳过置灰的格子。

上一版让诊断页学会了「媒体通道可能不存在」;这一版是同一条规则的写入一侧——规则属于寄存器家族,不属于最先发现它的那个面板。

诊断页:对模块没有的媒体通道,不再给出「测量值」

Page 14h 的诊断数据按侧命名(Table 8-139):MediaSideSNRLane<i>、MediaSideBERLane<i>,以及「媒体通道 1–4 / 5–8 的误码与比特计数」——都是媒体通道。

相干模块把 8 条主机通道汇进一路光载波,只有 1 条媒体通道,00h:210 会说明缺哪几条。Monitoring 和 Flags 早已照此处理(不存在的媒体通道显示 n/a),诊断页却没有。

⚠ 在 mock_coherent 上,SNR、BER、误码计数三张表都给出了8 条媒体侧读数,其中 7 条是模块根本没有的通道——比如第 8 条的媒体 BER 显示为 9.92e-05,那是对「不存在的东西」的测量。

现在这三张表对不存在的媒体通道显示 n/a,悬停说明依据是 00h:210;接口里对应的值为 null,并附 media_lanes_present 列表。主机侧不受影响。

误码计数表还有一个反方向的问题:一条通道一个比特都没计数时,接口给出 BER 0.0——也就是「零误码」,这是一个结论;而页面只显示大于 0 的值,于是真正零误码的测量(比如一万亿比特里没有一个错)也显示成「—」。「没有测量」和「完美的测量」看上去一模一样。现在没计到比特时为 null(显示「—」),零误码显示为 0,并说明这是零计数而非测得的下限。

被拒绝的 Apply,此前其实已经动了模块

DataPath 页的 Apply 会拒绝模块会静默丢弃的请求,并说明:「this would report success and change nothing」。

⚠ 但这个判断是在写完之后才做的:极性翻转、Tx 输出关闭、暂存的 Application、DPDeinit 都已经先写下去了。其中 DPDeinit 和通道控制写下去就立即生效(Table 8-77、8-78)。实测:上一次 Apply 还在进行中时,再按一次带着 DPDeinit 和 Tx 关闭的 Apply——提示「被拒绝、什么都没变」,一秒后所有数据通路都掉到了 DPDeactivated,通道 1–4 的 Tx 输出也被关了。

这不只是上一版加的那一条。检查下来,五种拒绝全部如此:配置进行中、数据通路处于过渡态、非初始化态下的 ApplyImmediate、模块不支持 ApplyImmediate、以及同时要两个触发器。

现在这五种判断都挪到了任何写入之前:被拒绝的请求对 Page 10h 一个字节都不写,提示说「什么都没变」就真的什么都没变。不被拒绝的请求照常写入,规范要求的「DPDeinit 与 Apply 同一次写入」的释放流程也不受影响。

一个已经生效了的「拒绝」,比不拒绝更糟——它恰好在模块发生变化的那一刻,告诉操作员去别处找原因。

演示模块:两个端口可以同时重配

上一节的规则是按数据通路的:规范 6.2.4.2 说模块忽略的是「那些通道上的新触发」,并且「不在那些通道所属的数据通路上执行」——不是整个模块。工具从 v2.115.0 起就是这样判断的。

⚠ 内置的演示模块却比规范更严:它整个模块只有一个「进行中的命令」槽位,槽位被占着的时候任何触发都被丢掉。于是在 mock_fr4x2(两个 400G 端口)上,端口 1 正在重配时对空闲的端口 2 按 Apply,工具正确地放行了,演示模块却悄悄扔掉——通道 5–8 从没进入 ConfigInProgress,生效的 Application 也没变。

一个比规范更严的演示模块,教给人的是一条规范里没有的规矩。现在演示模块每条数据通路各自跑自己的命令、各自计时:两个端口可以同时重配、各自报告结果;一次触发如果同时点到忙和闲的两条数据通路,只在闲的那条上执行;忙的那条仍然照规范忽略。

上一次 Apply 还没做完,再按一次就被模块悄悄扔掉

规范 6.2.4.2:

「当某条数据通路的通道上,先前触发的配置命令仍在处理中时,模块忽略这些通道上的新触发……因配置进行中而忽略触发位,不会向主机提示。」

工具此前已经拦下了 6.2.4 里另外两种「静默丢弃」——数据通路处于过渡态、以及在非初始化状态下用 ApplyImmediate——唯独漏了这一种。

⚠ 实测:第一次 Apply 之后,所有通道的 Config Status 都是 ConfigInProgress;紧接着再按一次,工具回复「已应用到通道 1–8」——而模块已经把它丢了。

现在,只要本次要触发的通道里有任何一条仍在 ConfigInProgress,请求就会被拒绝,并点名是哪几条通道;不会写出触发位。等上一条命令出结果(Monitoring 页 Config Status 列)再按即可。

  • 和「过渡态」那条不同,这条对所有模块都成立——规范对「过渡态」的忠告只针对支持无干预重配的模块,而 Table 6-3 和 6-4 的每一种配置流程都以「ConfigStatus = ConfigInProgress」开头。
  • 按数据通路判断。一个带两个 400G 端口的模块,一个端口正在重配时,对另一个端口的 Apply 照常放行。
  • 被拒绝的上一条命令不算「进行中」——它已经结束了,修正后可以立即再次 Apply。

媒体通道切换:禁用时按 Commit,模块什么都不做,也什么都不说

Table 8-196 对 EnableMediaLaneRedirection(6Dh:152)的定义是:

「0b:禁用——commit 命令没有效果。」

注意是「没有效果」,不是「被拒绝」:模块什么都不改,也不写任何 RedirectionCommitResult,所以它从不说自己忽略了什么。

⚠ 工具此前照样写下 commit,回复「已提交、已完成」,页面弹出绿色的 Redirection committed;表下接着提示「press Commit」——也就是刚按过、并且再按还是无效的那个按钮。更糟的是页面每次请求都带上 Enable 复选框的状态,复选框没勾时,每一次 Commit 都变成「先禁用、再提交一个不可能发生的 commit」。

现在这种 commit 会被直接拒绝,且在写任何东西之前——同一请求里的映射也不会被暂存,不会留下半截操作。判断时按「这次请求自己的 Enable 已经写入之后」来算,因为 Enable 先写、Commit 后写。6Dh 按 bank 分组启用,任何一组处于禁用都会被拒绝,错误信息会点名是哪一组。只「暂存」(Stage)不受影响——那本来就是启用之前准备映射用的。

表下的提示也改了:模块处于禁用状态时,它会说「先勾 Enable,再 Commit」,而不是让你再按一次 Commit。

结果列按类着色。Table 8-196 的结果码 3–6 都是拒绝,大于 6 的是保留值。此前它们全部以同一种中性文字显示,「Rejected: conflicts with active DataPath」和「Success」看上去是同一类回答,保留码则显示成「Code 7」。现在成功为绿、执行中为黄、拒绝为红,保留码写作「Reserved (7)」。

通道极性:同样八个位,在宽模块上是三个意思

Module Info 里的 Default Polarity 读的是 01h:171-172,一共八个位。规范 8.4.13 说得很清楚:

「当模块支持多于八条通道时,这里定义的通道极性适用于每一组八条通道,除非模块声明(见 Table 8-58)支持在 Page 60h 上做逐通道说明。」

所以这八个位到底在说哪些通道,取决于通道数和一项声明,而不是取决于寄存器本身:

  • 不超过八条 —— 就是这个模块的通道,无须多说
  • 更宽、且有 Page 60h —— 它们只描述第一组八条通道;逐通道的实际状态在 Page 60h 上(8.30.1)
  • 更宽、且没有 Page 60h —— 第 1 通道那一位同时也是第 9、第 17 通道的,模块没有别的地方可以另行说明
⚠ 工具此前不管哪种情况都只列八条通道。第三种情况代价最大:一个 16 通道、没有 Page 60h 的模块,明明在说「第 1 和第 9 通道是反的」,那一行却对第 9 通道只字不提——照着它接线,十六条里有八条会接反。

现在这一行会按实际适用的通道铺开(第三种情况下列出 1、9),并在后面注明它说的是哪一组通道、依据是哪一节。

Page 60h 的极性表:每个 bank 都从 1 号通道重新编号

规范 8.30 说「Page 60h 的每个 bank 对应 8 条通道」。工具把各 bank 读到的结果直接首尾相接,却没有重新编号——于是一个 24 通道模块返回的数据里,有三条通道都叫「1 号」。

界面上那张表是按位置渲染的,所以看着是对的;错的是每一条数据自己声称的通道号。这种错法不会在屏幕上露馅,只会在有人拿这份数据去对通道时才发作。现在跨 bank 统一编号为 1…N。

极性表底下那段说明,讲的是另一张表

⚠ 「Lane Polarity Status」表下面挂着一段讲标志读后自清、●! 历史标记、DP Changed 的文字——那是「Lane Flags」表的说明,而 Lane Flags 卡片下面一句说明都没有。

放在极性表下面它是错的:60h:128-129 是 RO(Table 8-188),不是 RO/COR——那里没有任何东西是锁存的,读它不清除任何东西,这张表里也没有 DP Changed 这一列。工具自己那张「读后自清」清单里本来就没有 Page 60h。两段说明现在都回到了各自的表下面。

Recall 那一列,从来没跟模块声明的缓冲区数量对过

信号完整性表里,Tx EQ Recall 填的是缓冲区编号(10h:154-155,Table 8-83:01b 是 1 号、10b 是 2 号);而 01h:161.6-5 声明的是缓冲区数量(Table 8-54:01b 表示一个、10b 表示两个)。两者本来就该比一比,而工具从来没比过。

⚠ 于是在一个只有一个缓冲区的模块上,某条通道暂存的「buffer 2」会和真正有效的值一样显示成绿色——而模块根本没有那个缓冲区可以调用。

这一列本来就被单独拎出来渲染过(编号不是量值,1 和 2 是两个缓冲区的名字,不是「更大 / 更小」),而一旦离开通用单元格,它也就离开了通用单元格里那两道「对照模块声明」的检查——旁边的 Tx Input EQ 有上限检查,Rx Amplitude 有编码集检查,只有它什么都没有。

这一列比旁边几列更要紧。规范 6.2.5 说其它暂存的信号完整性值只在 ExplicitControl 置位时才被采用(而本工具写的是清零),唯独 recall 例外——「recall,如果支持,在 ExplicitControl 未置位时同样生效」。所以它是本工具每一次 Apply 都会真正带上的那一个。

现在越界的那一格标红,并写明模块声明了几个缓冲区、以及 Apply 带上它会收到 ConfigRejectedInvalidSI。11b 仍按「保留值」单独标注——它根本没指向任何缓冲区,和「指向一个不存在的缓冲区」是两种不同的错。

声明本身是保留值(11b)时,表下会明说。那种情况下模块没告诉你它有几个缓冲区,下面的编号一个都没法核对;而一张会检查别的列的表在这里一声不吭,读起来就像「查过了,没问题」。

模块控制面板里那一位,从来就不是状态

Table 8-3 里另外两种访问类型让「读」本身撒谎,而 Lower 26.3 的 SoftwareReset 正是其中之一(Table 8-11 把它定为 WO/SC):

WO/SC —— 「从一个 WO/SC 元素读出的值为零,除非读得太早——在模块尚未评估并清除所写入的非零位之前。」

工具里有两个地方相信了这一位。

一是面板。它和另外四个 RW 位并排显示在同一列状态点里,悬停提示写着「Reset in progress」或「Idle」。两个都不对:不管模块在干什么,那个点都是灭的;而它唯一可能亮的时刻,意思是这次读发生得太早,不是「正在复位」。

⚠ 二是写入路径,这一处更严重。字节 0x1A 把几个互不相干的控制打包在一起,所以每次改动都先读回来再合并(这本身是早先一轮的修复:免得切低功耗时顺手清掉 SquelchMethodSelect)。合并却是从读回来的整个字节开始的——于是一次落在那个瞬态窗口里的读,会把第 3 位原样写回去:在一次毫不相干的改动中间,又触发了一次软复位,没有任何人要求过它。

这个窗口等不过去。「evaluated and cleared」在整份规范里只出现一次,就在 Table 8-3,旁边没有给任何时间。所以读-改-写永远无法确认自己已经在窗口之外,只能不信任读回来的那一位:现在合并前先把写-only 的触发位剥掉,只有明确点名要复位的调用者才能触发它——「复位模块」按钮照常工作。

面板那一格现在写的是 WO/SC trigger,不再是一个状态点;访问类型由后端随数值一起送来,页面不另存一份——同一张规范表抄两遍,正是两边开始打架的方式。另外四个位是 RW,照常显示状态。

裸寄存器面板会把模块的故障记录读没了

规范 Table 8-3 定义了六种访问类型,其中一种让「读」本身成为破坏性操作:

RO/COR —— 「一个 RO/COR 字节中的所有位,在该字节被读取之后由模块清零。」

这些字节就是锁存标志——模块记录「发生过某件事」的地方:某条数据通路弹过、某个检测器失锁过、某次调谐被拒绝过。模块不保留第二份。本工具每一个会读这些字节的面板,都会把结果折进「标志历史」,正是为了这个原因;而裸寄存器面板不会——在那里它们只是一串数字。

⚠ 于是在这个面板上读一次 11h:134,模块攒下来的故障记录就没了,而且没有任何提示。十六进制转储看起来完全一样——不管那些字节里原本有没有东西。

六个块,包括两个本工具没有面板、但这个面板能够到的:模块级标志(Lower 8-13)、通道标志(11h:134-153)、激光器调谐标志(12h:231-238)、诊断标志(14h:132-139)、Network Path 标志(17h:128)、VDM 门限穿越标志(2Ch 整页)。12h:230 故意不在其中——那个汇总寄存器是普通 RO,读它不清任何东西。

这条数据通路走的是哪几条媒介通道(7.9.1)

主机选的是主机侧通道;媒介侧通道是跟着算出来的,规范 7.9.1 把这个推导定死了:

「第一个 Application 实例(按主机通道编号顺序)将使用该 Application 所通告的、编号最低且可用的媒介通道起始的通道组,这会占用一组连续编号的媒介通道。第二个 Application 将使用下一个编号最低的可用媒介通道起始的通道组,依此类推。」

而这个结果此前没有任何地方报告过。在不支持媒介通道交换的模块上,它不是一个寄存器——规范也不需要一个,因为规则已经决定了它;而本工具从来没有把它算出来。

⚠ 与此同时,Monitoring 表把「媒介侧的测量值」和「主机侧的状态」放在同一个行号上,而 CMIS 对两侧是独立编号的。Table 8-99 的标题就是「Media Lane-Specific Monitors」——Tx/Rx 光功率和 Tx 偏置按媒介通道索引;而 DataPath State、Config Status 按主机通道。当 Application 的媒介宽度等于主机宽度时两者正好对齐,什么问题都没有;不相等时就会错开——两条 4H/1M 的相干数据通路,主机通道 5-8 其实测在媒介通道 2 上,而媒介通道 5 不属于任何一条数据通路。

现在 DataPath 面板的每条数据通路会写明它占用哪几条媒介通道(例如 media 1–4),悬停说明里指明这正是 Monitoring 表里衡量它的那几行。

输入本来就在读,只是没送到该去的地方。MediaLaneAssignmentOptions(01h:176-190)一直以原始位图印在 Applications 页签上;而 DataPath 的两个端点解析描述符时把这一整块传成了空,于是那条路径上这个字段恒为「未声明」。现在两处都传了,并且按连接缓存——它是静态通告,而 DataPath 面板每次刷新都要用。

只答第一个 bank,再往后不作答。7.9.1 说「每个 bank(即 8 条主机通道一组)总是有 8 条外部媒介通道」,所以这个池子不会越过通道 8 继续往下数;而 8.3.7 更说了,超过 8 条通道的模块根本无法无歧义地声明自己的媒介通道。分配怎么跨 bank 延续,规范没有写——替它回答就是凭空造规则。同理,媒介宽度超过一个 bank 的数据通路也不给答案,而不是去编号这个 bank 根本没有的第 9-12 条。

支持媒介通道交换的模块会标注「nominal」。那类模块可以改写这个映射,它实际提交的映射在 Page 6Dh 上,那才是真相。

这个 Application 能从哪条通道开始(HostLaneAssignmentOptions)

规范 6.2.3.2.1 把这件事写成对主机的义务:「主机必须按模块为该 Application 通告的 Lane Assignment Options 来分配通道」。这个字段是 Application 描述符的第 4 个字节:「位 0-7 构成对应主机通道 1-8 的位图。位为 1 表示该 Application 的通道组可以从对应的主机通道开始」。

工具一直在读这个字节,也一直把它以原始位图的形式印在 Applications 页签上。而真正做选择的地方是 DataPath 面板——那里的下拉框把每个 Application 都列在每条通道上,对此只字不提。操作员要等到 Apply 之后,再去把一个 4 位的状态码ConfigRejectedInvalidDataPath(4h)翻译出来才知道。

本版把规则放到了做选择的那一刻:

  • 下拉框每一项后面都写明这个 Application 能从哪几条通道开始,例如「App 2 — 400GBASE-DR4 4H/4M · begins on 1, 5」。
  • 当前暂存的配置里若有数据通路起始在不被允许的通道上,那一行会标出「may not begin here」,并说明模块通告的是哪几条、以及模块会回哪个状态码。
⚠ 但写入照样放行——这是有意的。本工具划的那条线是:模块会不会作答。模块会默默吞掉的写入,工具替你拦(否则「提示已应用、实际什么都没做」是最难查的一种);而数据通路起始越界,模块会在 ConfigStatusLane 里指名道姓地回一个代码。看真实模块拿到一个非法分配会怎么做,本来就是这个工具存在的理由之一。所以规则在写入之前提示,写入本身照旧。

规则管的是「起始」,不是「哪条通道带哪个码」。一个 4 通道的 Application 从通道 1 起,会占用通道 2-4,主机要把同一个 AppSel 写进这四条——后三条是延续通道,位图对它们只字未提。若拿每条通道去对位图,一块完全合规的模块上每四条就会有三条被误标。

位图只有 8 位,对应通道 1-8。超过 8 通道的模块上,规范没有说这 8 个位怎么延伸——通道 9 是不是「bank 1 的通道 1」,还是干脆不在覆盖范围内。所以检查到通道 8 为止,再往后不作判断:替规范回答一个它没回答的问题,等于凭空造一条规则。16 通道的演示模块因此不会被误标。

诊断标志也一样,而且上一版这句话说错了(13h:206-213)

⚠ 先更正:上一版说「12h:239-246 是规范里唯一默认屏蔽的一组」,这是错的。四组里有两组默认屏蔽——除了激光器调谐那组,诊断屏蔽位(13h:206-213)也是,Table 8-133 用一句话写明:「本页所有屏蔽位的默认值为 1(屏蔽)」。另外两组(模块级与通道级)则根本没有规定默认值。这句错话进了工具提示、手册、skill 和发布说明,现在全部改正。

更正的同时也发现:被我说错的那一组,本身就有和上一轮完全相同的毛病。诊断标志在 14h:132-139——参考时钟丢失、各通道门控完成、图案发生器失锁、图案检测器失锁——工具把它们全都读了、还记了历史,而它们的屏蔽位在 13h:206-213,一个都没读。所以一块没人配置过的模块,跑 BER 时检测器中途失锁,主机根本不会被中断,而 PRBS 面板说不出这件事。

现在 LOL 那一列会标注:亮着的标志和历史记录里的标志若被屏蔽都会加 masked;安静的通道只在 tooltip 里说明——因为默认就是屏蔽,四张表全铺上「masked」只会没人看。参考时钟那条提示同理(它的屏蔽位是 13h:206.7,按模块而非按通道)。

顺带修正了块长度。工具此前把这一对按 18 字节配对(14h:132-149 对 13h:206-223),两张总览表确实都这么写。但明细表说了算:Table 8-138 的标志到 139 为止,Table 8-133 的屏蔽位到 213 为止、并把 214-223 标为 Reserved[10],而 Page 14h 总览自己的下一行也把 140-149 标为 Reserved[10]——也就是说那张总览表自相矛盾,而它的 Reserved 行与明细表一致。已对照渲染出的原始页面核实,不是文本抽取错位。目前还没有代码用到这个长度,这是它一直无害的唯一原因。

演示模块此前也不合规。它从不写 13h:206-213,读作「全不屏蔽」;现在按规范默认屏蔽,而且 206 只置定义了的 bit 7(6-0 是 Reserved)、207 保持 0。mock_dr8 则清掉了 212 的低两位——一个真在通道 1、2 上跑误码测试的主机会这么做——这样两种分支才会同时出现。

线缆本身要走多久(01h:148-149)

规范 Table 8-50:「不可分离 AOC 的传播时延,以 10 ns 为单位、四舍五入到最近的 10 ns,为 0 表示未规定」。这个字段从解析器写好那天就解对了,却一处都没显示过。

而且也没有模块可以承载它:此前每一个分页 profile 的媒介都是可插拔的,唯一的线缆组件 mock_flat_dac 是平坦内存、连 Page 01h 都没有。所以本版新增了 mock_aoc——一根 20 m 的 400G 有源光缆,正是这个寄存器所定义的那种模块。它顺带给另一条此前无人可测的分支补上了真实模块:媒介类型 04h 同时涵盖有源铜缆与有源光缆,而有源光缆用「全 0」回答铜缆衰减、从而让那一行自动消失。

⚠ CDB Background Mode(163.5)清零时,模块在命令执行期间会停止响应「任何寄存器」的访问——不只是 CDB 那几页,是整个管理接口。在这种模块上一边跑固件升级一边轮询监控值,不是「慢」,是根本没人理你。写成单纯的「不支持」会让人以为只是少了个便利功能。

CDB Max Busy 是主机在判定模块已经停摆之前必须愿意等的时间。这一行带一个 ▲ 标记,原因是 OIF-CMIS-05.4 的 Table 8-55 在这里自相矛盾:

基本 Application 描述符最多只能有 15 条。规范 6.2.1.6.2 为此引入了 Normalized Application Descriptor(NAD),一个模块最多可以通告 255 × 15 = 3825 个 Application,放在分 bank 的 Page 1Ch 上:

Application 编号 AN = 15 × 块号 + AppSel 码。要选中其中一个,两半都得给:AppSelCode 和 NADBlockIndex——AppSel 码在每个块里都是 1..15,单给一个没有意义。面板上每一行都同时列出这两个值。

块 0 必须是基本描述符的镜像(6.2.1.6.2)。工具会逐条核对,不一致就标出来——这意味着模块在同一个 AppSel 码下通告了两个不同的 Application。核对时不能简单地比相等:GID 非零时基本描述符里本来就应该是 BEh,把这种情况报成不一致,等于说每个做对了的模块都是坏的。

目前的限制:工具能读全部 NAD,但还不能配置块 0 以外的 Application——那需要往 Staged Control Set 的 NADBlockIndex(18h:128-143)里写值,工具尚未写这个字段。面板上如实写明了这一点。

换页之后读回来核对一下

规范 8.2.15 写得很明确:「当主机写入会让 PageMapping 寄存器指向一个不受支持的页地址时,模块会清零 PageSelect 字节……使得 PageMapping 最终选中 Page 00h」。

⚠ 也就是说,请求一个模块没有的页,任何一步都不会报错:写入被接受,没有任何提示,而之后每一次读都落在 Page 00h——厂商标识信息——并被按调用方期待的格式解码。一次不会失败的读取,不等于一次成功的读取。

规范把答案放在了寄存器里,所以现在读回来核对:每个页在一次连接中只核一次(模块插着不动时,它支持什么不会变;若每次换页都读回,会让每次面板刷新的总线流量翻倍)。页不对就明确报错,并写清模块回了什么。

诊断页也要先看广告

01h:142.5 DiagnosticPagesSupported(「支持 Banked Pages 13h-14h」)在连接时就解析了,却从来没有人去问它。本工具里其它每一个可选页都按各自的广告门控——0Ch、60h、61h、62h 各有一条,就写在同一个函数里相隔三行的地方——唯独诊断这一族没有。

于是在没有这两页的模块上,页选择被清零、Page 00h 一直映射着,厂商信息被解码成环回能力、图案支持情况和误码计数。现在环回、PRBS、SNR、BER、比特与错误计数这几个面板会在触碰页之前就明确拒绝,并点名 01h:142.5。

为什么一直没被发现:内置的演示模块全都实现了 13h/14h,而那条「每个演示模块、每个端点,都不许读到不存在的页」的巡检,力度只能到夹具为止。

平坦内存模块:工具不再读一个它没有的页

规范:「与分页内存模块不同,平坦内存模块不支持动态换页进入上层内存」。而工具在连接时读取的全部通告——有哪些监控、多少条通道、各瞬态最长多久、标称波长是多少——统统住在 Page 01h。

⚠ 平坦模块对这些地址的读取会从 Page 00h 作答,而 Page 00h 那一段是厂商名、料号、序列号。于是读回来的是 ASCII,却被当成能力位解码,并作为「这个模块的通告」显示出来。在新增的无源铜缆 DAC 演示模块上实测,修复前:一根铜缆被解出 873.85 nm 的标称发射波长、被宣称带 Rx 光功率监控,换页保持时间被解成 0.3 微秒(规范默认 10 毫秒)。没有一条是真的,也没有一条看起来不对。

内存模型本身在 Lower Memory(每个模块都有),所以现在先读它;模块说自己是平坦的,就根本不去读 Page 01h,那些通告缺席而不是被捏造。

再进一步:规范 8.2 说平坦内存模块就是静态内存模块(「只提供只读的、不可变的数据」),而 Table 8-9 与 Table 8-10 的标题写着「not for static memory modules」——也就是说模块级标志与监控值本来就不存在于这类模块。所以工具把它们记为「通告为无」,而不是「未知」:未知在下游一律等于「全都显示」。Memory Model 那一行现在会直接说明这一点,免得满屏空行看起来像读取失败。

新增演示模块 mock_flat_dac(无源铜缆 DAC,平坦内存)。此前所有演示模块都是分页的,没有任何东西能暴露这个问题。

平坦内存模块:描述符第 4 字节不是通道分配位图

Application Descriptor 的第 4 字节,两种模块上是两个完全不同的字段:Table 8-22(分页内存模块)把它给了 HostLaneAssignmentOptions——一张位图,说明这个 Application 可以从哪些主机侧通道开始;而 Table 8-23(平坦内存模块)把同一个字节给了 HostInterfaceGID,即定义 HostInterfaceID 的那张 SFF-8024 表的组号。

⚠ 工具此前对两种模块都按位图读。于是在平坦内存模块上,GID 为 1 就成了「可从主机通道 1 开始」,GID 为 2 就成了「通道 2」——看起来很像样的答案,回答的却是模块根本没被问到的问题,而且这个假位图还会进入计算模块通道容量的贪心装箱。实测影响:两个各 4 通道的 Application,GID 分别是 01h 和 10h 时,按位图读会被当成互不重叠,模块因此被记成 8 条主机通道——而它从未宣称过。

现在:平坦内存模块根本没有通道分配掩码(是「没有这个字段」,不是「掩码为 0」),该字节按本来面目显示为 GID 0x__,鼠标悬停会说明这是 Table 8-23 的 HostInterfaceGID、不是通道分配;分页模块一切照旧。容量计算也不再把它当成起始通道。

规范在这一处自己有个小矛盾:GID 那一行写的是 bit 7-0,紧接着又把同一字节的 bit 3-0 标为保留。工具原样显示整个字节,不去替规范决定该怎么移位。

Application 的通道数栏:0 不是「0 条」

规范 Table 8-22 把 Application Descriptor 第 3 字节的两个半字节写得很清楚:「0000b:通道数由接口 ID 决定,或显式给出:0001b:1 条 …… 1000b:8 条。1001b–1111b:保留」。

⚠ 也就是说 0 不是「这个 Application 没有通道」,而是模块不再重复一个它的接口 ID 本来就已确定的宽度;而 9–15 根本不是通道数。此前工具把两者都当数字用:前者在 Application 表里显示成一个破折号、在 Host Lanes 下面的分解里显示成「0H/0M」;后者被当成 9–15 条通道,还加进了模块对外宣称的通道总数。

现在这两种情况分别显示 H=per interface ID 和 H=Reserved (Fh),都不计入通道总数——要把「由接口 ID 决定」解成具体数字,需要 SFF-8024 里接口 ID 对应的通道数,那张表本工具没有收录,所以它说明是哪一种,而不是编一个数字出来。(4H/4M 这种正常宽度显示不变;H/M 只在跟着数字时才当单位用。)

接口 ID 显示 BE 时:去看 NAD

同一张 Table 8-22 对两个接口 ID 字节都写了:「BEh:接口 UID 的 GID 非零,因此必须查阅对应的 NAD」。这是规范定义过的编码,不是 SFF-8024 表里缺的一项,而工具此前显示 Unknown (0xBE)——就在同一块面板上,工具其实已经在告诉你这个模块宣称了几组 Normalized Application Descriptor。现在显示 See NAD (0xBE)。

「Unknown」只在工具真的不知道时才会出现

「Unknown」是在说工具,不是在说模块。它告诉你工具没认出模块给的值,你合理的反应是去找个更新的工具。所以对于规范本身已经定义过的编码,它不该出现。

⚠ 此前两处正好犯了这个毛病,而且都在你最先看到的那块面板上:Media Type(Lower 85)规范 Table 8-20 把整个字节都定义了——06h–3Fh 保留、40h–8Fh 自定义、90h–FFh 保留——工具却把 05h 以上一律显示成 Unknown;Media Interface(00h:212)规范 Table 8-41 到 14h 为止、15h–FFh 保留,而工具的表只到 11h,于是 12h/13h/14h 这三种已定义的铜缆线性均衡技术在对应模块上全被显示成 Unknown。

现在:落在保留区间的显示 Reserved (0x__),落在自定义区间的显示 Custom (0x__),并且都带上原始编码——保留编码是关于模块的问题,自定义编码则意味着这块模块的 Application Descriptor 要按厂商自己的 ID 表去读,这件事在动手解读之前就该知道。缺的三种铜缆技术已补齐并各自区分(近端+远端 / 远端 / 近端线性有源均衡);0Fh 在 CMIS 5.4 里标了「不要用于新设计」,名称里现在也写明已弃用。

工具确实不知道的地方仍然写 Unknown:连接器类型、SFF-8024 标识符、主机接口 ID 这几张表定义在 SFF-8024 里,本工具没有收录,写 Unknown 是实话。

没有逐通道环回的模块,勾一条不再被拒绝

规范 Table 8-131 对四个环回使能字节都写了同一句话:「若『支持逐通道环回』位为 1,环回按通道控制;否则,只要有任何一个使能位置 1,该侧所有通道都进入环回」。

⚠ 也就是说,在不支持逐通道环回的模块上只勾一条通道并不是错误——模块会把该侧全部通道都环回。工具此前直接拒绝了这种请求,等于凭空造了一条模块并没有的限制,而且操作员在自己想明白「必须全选」之前根本没法用环回。

现在这种请求照做,并且把掩码扩成全通道再下发、在返回里说明「已应用到全部通道」。为什么要扩而不是原样写:这个寄存器会被读回到同一个面板——写 0x01 而模块实际环回了 8 条,面板就会显示「1 条在环回」,而真相是 8 条。
清零不会被扩(那是关环回,扩了就变成开);支持逐通道的模块照旧按你勾的来;模块压根没有某个方向的环回时,仍然明确拒绝——那是另一个答案。

Page 62h 的阈值也是每条媒体侧通道一套

Table 8-192 对 62h:128–191 的描述就是「每条媒体侧通道的告警和警告阈值」。工具此前把这份列表按主机侧通道数截断,于是相干模块拿到 8 套阈值,其中 7 套属于它根本没有的媒体侧通道。

ℹ 这是同一个轴搞错的第三处:光功率监控(Table 8-99)、调谐表(8.15)、现在是阈值(Table 8-192)。三处现在共用同一个判断,不是三套规则。
Monitoring 里也一样:没有媒体侧通道的那些行既没有读数、也不再挂阈值窗口——给一个不存在的读数配阈值是没有意义的。

调谐表也是按媒体侧通道排的

规范 8.15 写得很直接：「Page 12h 的每个 Bank 对应 8 条媒体侧通道」，而 Table 8-108 里每一项——栅格间隔、通道号、微调偏移、激光器频率、目标输出功率——都是「每条媒体侧通道一个」。

⚠ 调谐表此前是按主机侧通道排的。相干模块只有一路激光器，却被排出 8 行——后 7 行读的是不存在的寄存器。
更严重的是写：给「第 5 通道」下调谐会被接受并写下去，然后界面把通道号从一个模块根本没有的媒体侧通道读回来显示——操作员以为调好了。

现在调谐表只列真实存在的媒体侧通道，对不存在的通道下调谐会被拒绝并说明依据（00h:210 和 8.15）。并且沿用同一条规矩：一次请求里只要有一条通道不合法，一个字节都不写。

ℹ 和上一条一样，超过 8 条通道的模块不受此限制——规范 8.3.7 说这类模块无法无歧义地声明，所以工具不据此隐藏任何通道。

相干模块只有一条媒体侧通道,别的行不是读数

Monitoring 表里每一行是一条主机侧通道,但其中三列—— Tx Power、Tx Bias、Rx Power ——规范(Table 8-99)叫的是「媒体侧通道监控」。

⚠ 相干模块把 8 条主机侧通道汇进 1 路光载波,所以它只有一条媒体侧通道。第 2–8 行读的是模块声明自己没有的媒体侧通道的寄存器——读出来是 0,而 0.0 µW 是 dBm 量程的底部,正是界面涂成告警红的那个值。
这和「模块没实现这项监控」是同一个错,只是换了一个轴。

00h:210(Table 8-36)就是模块自己说的哪几条媒体侧通道不存在。工具一直在读这个寄存器,只是没有任何地方用它。现在这三列在不存在的媒体侧通道上显示「no such media lane」,和「not implemented」分开写——两者是不同的答案,要查的寄存器也不同。

ℹ 超过 8 条通道的模块不用这个寄存器:规范 8.3.7 自己说了,这类模块「无法无歧义地声明哪些媒体侧通道不受支持」——一句有歧义的话,只用它的一半并不会更安全。
DataPath State、Output、Config Status 这几列是主机侧的,每一行照常显示。

标志亮着、中断却没来：那是被屏蔽了

规范用一句话定义了中断线：「只要有任何一个标志置位、且它对应的屏蔽位是清零的，Interrupt 就保持有效」。也就是说中断状态不是另外一个要读的东西——它就是标志和屏蔽位的组合结果。

ℹ 所以真正有用的是两者不一致的时候：界面上标志亮着、Interrupt 却显示没有请求，就说明这个标志被屏蔽了——模块记下了这件事，但不会去打扰主机。排查「为什么我的主机没收到告警」时，这一行直接给出答案。
屏蔽位的位置：模块级标志 Lower 8–13 对应Lower 31–36；通道标志 11h:134–153 对应 10h:213–232；诊断标志 14h:132–149 对应 13h:206–223。

这个值工具一直都在算（接口里就有），只是界面从来没显示过，两份手册也都没提。演示模块那边则是反过来：中断位被写死成「没有请求」，于是它可以一边挂着温度告警、发送故障和失锁的检测器，一边报告自己没在找主机。现在两边都按规范那句话来。

Aux 监控的告警标志：读一次就没了

下部内存 9–11（Table 8-9）放的是六个模块级监控各自的四个阈值标志（高/低告警、高/低警告），三个字节排法完全一样：

字节位 3–0位 7–4
Lower 9温度供电电压
Lower 10Aux1Aux2
Lower 11Aux3自定义监控
⚠ 这整个块都是 RO/COR：读它的那次读就把它清掉了。工具每次轮询都一次性读 8–13，以前只解析第 9 字节——于是 Aux 和自定义监控的告警被读走、被丢掉，而且没给任何人留下：下一个读它的人只会看到 0。模块侧面板的 Alarms 一行还写着 0x08–0x0D，却对其中两个字节一概不知。

现在 Aux 每一行的读数后面直接跟着模块自己的判决（高告警 / 低告警 / 高警告 / 低警告），告警红、警告黄；没有标志就什么都不显示。因为标志是读后即清的，它说的是“上一次轮询以来”，不是“此刻”；历史区会把它留下。

ℹ 标志归属于监控（§8.14.1），而这六个监控全是可选的（01h:159，Table 8-53）。模块没声明的监控，其标志按“未知”处理而不是“正常”——不存在的标志读回来也是 0，和一个健康的监控一模一样。
自定义监控（Lower 24–25）的编码规范里写的是“S16 或 U16”，由厂商自定，所以工具不会编一个数值出来；它声明了这个监控时，只单列一行显示模块的判决。

Tx 偏置电流的刻度倍数

Tx 偏置寄存器数的是 2 µA 的个数，但 01h:160.4-3（Table 8-53）还给它一个 ×1 / ×2 / ×4 的倍数。工具此前把刻度写死成 2 µA， 从不读这两位。

⚠ 后果不是“少显示一个字段”，而是 数值错了 2 倍或 4 倍——监控读数和阀值都错。
而且这不是假想情况：16 位寄存器 × 2 µA 的上限只有 131.07 mA，所以偏置高于这个值的模块（相干模块很常见） 必须声明 ×2 或 ×4。现在监控与阀值都按声明的倍数换算。
ℹ 内置的 mock_coherent_zr 现在工作在 180 mA、声明 ×2—— 正好超过 ×1 能表达的上限，方便你验证主机软件有没有处理这个倍数。 规范里 11b 是保留值，工具按 ×1 处理，不会自作主张地把读数放大四倍。

读了却没解析的那一个字节

通道标志在 11h:134–153是连续的，工具一次性读 20 个字节——真实硬件上这比 20 次切页加等待快得多。但其中只解析了 19 个：0x8A（Tx 自适应均衡失败）被跳过了。

⚠ 这一整块是读后即清的，所以「读了不用」和「没读」完全不是一回事：这个读动作把标志消耗掉了，谁也再看不到。
更能说明问题的是：这个标志的能力声明（01h:157.3）工具是读了的，接口返回里明确写着模块支持它——却没有任何一条通道带着它的值。

现在 Lane Flags 表里多了一列 Tx AEQ Fail。它的含义值得单独说一句：自适应均衡没能收敛，意味着模块没能把主机发过来的信号均衡干净——问题在进模块的那段链路上（连接器、PCB、主机侧发送参数），而不是模块内部坏了。

模块没实现的标志，不再显示为“正常”

01h:157–158（Table 8-52）声明了模块到底实现了哪些 Flag： Tx Fault、Tx LOS、Tx CDR LOL、Tx 自适应均衡失败、Rx LOS、Rx CDR LOL。

⚠ 一个没实现的 Flag 读出来是 0， 而一个健康通道的 Flag 读出来也是 0——两者完全一样。 以前界面把它们都渲染成绿点，于是 “没人在监视这一项”看起来就像“这一项正常”。
现在未实现的 Flag 显示为灰色 n/a，悬停说明原因。 内置的 mock_sr8 故意不实现 Rx CDR LOL 和 Tx 自适应均衡失败两项。

16 通道以上模块的 SNR / BER：选错了窗口

Page 14h 是分 Bank 的（规范 8.17：「Page 14h 的每个 Bank 对应 8 条通道」）。诊断选择器 14h:128 和它选出来的结果窗口 14h:192–255 都在这一页里——也就是说，每个 Bank 有自己的选择器、自己的结果窗口。

⚠ SNR 和 BER 两个接口只在 Bank 0 里写了一次选择器，然后去每个 Bank 读结果窗口。于是在超过 8 通道的模块上，第 9 条往上的读数来自一个从没被选中的窗口——那里放的是上一次别的功能留下的数据。
实测（16 通道模块，Bank 1 停在误码计数窗口）：第 9–16 通道的 SNR 报成了 181 dB、163 dB 和一串 0.00——181 dB 一眼假，但 0.00 看上去就像一个测量值。

误码计数那个接口本来就是对的，代码里还写着这条规矩的注释——只是没推广到另外两个。现在三个接口共用同一个读取函数，在哪个 Bank 读就在哪个 Bank 选。

ℹ 8 通道模块只有一个 Bank，行为完全不变。受影响的是 16 / 24 通道这类模块（内置演示模块里的 mock_zr16、mock_1600g_16lane、mock_24lane）。

演示模块不再自相矛盾

01h:142.5（DiagnosticPagesSupported）声明 Page 13h–14h 存在。 所有内置演示模块都实现并提供这两页（PRBS、环回、BER、SNR、计数器都在里面）， 却一直声明“我没有这两页”。同样，它们报告温度、电压、光功率、偏置和各种 Flag， 却在 157–160 里声明“一个都没实现”。现已全部改为如实声明。

模块拒绝了你的配置时，页面会说实话

DataPath Config 里的 AppSelect 下拉框读的是 Page 10h 的 Staged Control Set ——也就是“你要求的”。模块实际在跑的是 Page 11h 的 Active Control Set（Table 8-92，206–234）。 平时两者一致，一旦 Apply 被拒绝就会分岔。

按 CMIS 8.13.3，Apply 分四步：命令受理 → 参数校验 → 执行 → 结果反馈。 校验不过时模块直接跳过执行步骤——那条通道继续跑原来的 Application， 数据通道也不会重启。

⚠ 以前这种情况下，下拉框会一直显示你选的那个 Application，看上去就像已经生效了。拒绝提示只弹 8 秒， 错过了就再也看不出来。
现在不一致的通道会在下拉框下方多一行红字 running App N，告诉你模块实际在跑什么； 鼠标悬停会写出两边的具体寄存器地址。
ℹ 什么时候会被拒绝：最常见的是选了模块没有声明过的 AppSelCode（ConfigRejectedInvalidAppSel，代码 3h）。下拉框只列出模块自己声明的 Application，所以正常操作不会碰到；但换了模块、或者通过 API 直接下发时就可能遇到。其它拒绝原因见 CMIS 5.4 Table 8-101， 包括通道不在 DPDeactivated（6h）、只给了 DataPath 的一部分通道（7h）等。
该表把 2h–Bh 和 Dh–Fh 整段都定义为拒绝，工具按代码范围判断， 不依赖名字拼写——模块返回一个规范里保留的拒绝码也不会被当成成功。
⚠ 以前所有拒绝长得一模一样。Table 8-101 给了八种不同的拒绝理由， 每一种对应你该改的东西都不同；旧版本只把枚举名原样显示出来， 等于只告诉你“被拒了”。而 9h–Bh（规范保留）和 Dh–Fh（厂商自定义） 这两段没有名字，于是 Monitoring 表按名字判色时把它们涂成了 “该 lane 未使用”的灰色——同一时刻弹出的红色提示却说配置被拒绝， 同一个寄存器，界面两处自相矛盾。
现在颜色改用代码区间判断，Config Status 单元格鼠标悬停会写出这条码 的含义和补救方向，Apply 提示也按理由分组给出同样的说明。

⚠ 「这条 lane 不用」以前在界面上说不出来。 规范 6.2.4.3 把 AppSel = 0000b 写成强制要求： 「主机必须给每一条未使用的 host lane 赋 AppSel = 0000b」， 而且缩窄一条数据通道时「任何变为未使用的 lane 都必须这样标出来」。 可下拉框只列模块声明过的 Application，没有 0 这一项—— 于是在这个页面上根本没法释放一条 lane。
反过来读也是错的：模块已经把 lane 5–8 置为未使用时， 表格照样显示「App 1 — 800GBASE-DR8 8H/8M」（因为没有值为 0 的选项， 浏览器只好选中第一项），而专门为这种情况做的 running … 红字提示也不会出现——它的判断条件 active && … 在 0 上短路了，偏偏 0 才是最需要提示的那个值。 这时候再按 Apply，下发的是「4 条 lane 跑 8-lane 的 App 1」，模块按 4h 拒绝： 一个界面自己造出来的死胡同。
现在下拉框第一项就是 — unused (AppSel 0) —， 模块运行中的 0 也能被正确选中；提示文字一律写「no Application」， 不再写成容易误读的「App 0」。
⚠ 换应用之前要先把数据通道停下来。 规范 6.2.4.3 把这条写了两遍：把一条正在用的 lane 释放成“未使用”， 以及改变一条数据通道的宽度（换成通道数不同的 Application）， 都只能在 DPDeactivated 状态下做。做不到就是 ConfigRejectedLanesInUse（6h，“有 lane 不在 DPDeactivated”）。
本工具内置的八个演示模块，声明的两个 Application 通道数都不一样 （8 lane 和 4 lane），所以在这些模块上任何一次换应用都要先停通道。 正确顺序是：
1）勾上要改的那条通道的 DP Deinit，按 Apply，等它显示 Deactivated；
2）选好新的 Application，取消 DP Deinit 勾选，再按一次 Apply。
只是重新下发同一个 Application（re-commission）不受这条限制， 把本来就空闲的 lane 编进通道也不受限制——空闲 lane 本来就是 Deactivated。
以前演示模块不检查这个前提，一律回 ConfigSuccess， 所以这个拒绝码从来没在界面上出现过， 工具也就从没提示过这个顺序。现在被拒时提示会直接写出该勾哪个框、按几次 Apply。
⚠ “停下来再改”这套动作以前是无效的。 规范 6.2.4.3 规定，改变一条数据通道的宽度只能在 DPDeactivated 下进行， 所以换应用是两步：先勾 DP Deinit + Apply 把通道停下， 再选新的 Application、取消勾选、Apply。
第二步是一次 Apply 同时带着新配置和释放，而工具写寄存器的顺序是 先写 DPDeinit、后写 AppSelect——释放的那一刻数据通道就开始重启， 模块按当时暂存区里的内容去承载，也就是旧的那个 Application。 于是通道原样起来，Config Status 还报 ConfigSuccess： 规范唯一允许的换应用流程，恰好是工具做不成的那个。
现在暂存区（AppSelect、两个极性掩码、Tx Disable）一律先于 DPDeinit 写入， 释放时模块看到的是你要的新配置。
ℹ 未使用的 lane 一定显示 Deactivated。 规范 6.2.3.2：AppSel 0000b「表示该 lane（及其相关资源）未被使用、不属于任何数据通道」， 并且「模块对未使用的 lane 始终报告 DPDeactivated 状态」。 内置演示模块以前不管配的是什么，只要被 Apply 选中就一路走到 Activated—— 于是一条没有任何 Application 的 lane 显示为绿色的“已激活”， 悬停还写着“数据通道已激活”。现在它按规范报 Deactivated。
判断依据取的是 Active Control Set（模块实际在跑的），不是 Staged Control Set——否则你在下拉框里选了 unused 还没按 Apply， 在跑的通道就会先被显示成已停止。
⚠ “Active Control Set”不等于“硬件正在跑的”。 DataPath Config 里下拉框下方的红字 running App N 读的是 Page 11h 的 Active Control Set。但规范里还有一个必备寄存器 DPInitPending（11h:235，Table 8-106）专门说明： ApplyDPInit 的 Provision 已经把暂存区拷进 Active Control Set， 但真正把它落到硬件的那次 DPInit 还没走—— 此时“Active Control Set 的内容可能与实际硬件配置不一致”。 工具以前从来没读过这个寄存器。
对于两种免干预流程都不支持的模块（规范 Table 6-4）， 这正是按 Apply 的正常结果：命令被接受、配置被拷贝， 但数据通道不会重启，硬件还在跑原来的配置， 要靠你自己把通道停一下再放开才生效。
现在这种通道会在下拉框下方多一行琥珀色的 awaiting DPInit，悬停写明寄存器位置、含义，以及怎么把它落实。 内置演示模块以前不管 Lower 02h 说什么都会重启通道， 所以 Table 6-4 那一类模块从来没被模拟过。
⚠ 超过 8 条通道的模块，PRBS 的 LOL 那一列以前是错的。 Page 14h 上那六个锁存标志字节——两侧的检测器失锁、 两侧的发生器失锁，以及两个门控完成标志—— 都是每条通道一个 bit，也就是每个 bank（8 条通道）一个字节。 而工具六个全都只读了 bank 0。
对超过 8 条通道的模块，这不是「少了个功能」，是答错了： 第 9 条通道显示的是第 1 条的标志， 而第 16 条通道失锁根本看不见。 检测器有没有失锁，本来就是这一列存在的全部意义。
标志历史还在下一层犯了同样的错： 它按 bit 位置记「谁闪过」，于是第 16 条通道的一次失锁 被记到了第 8 条头上—— 冤枉了一条本来好好的通道，又放过了真正出问题的那条。
现在六个字节都逐 bank 读，历史也按绝对通道号记。 8 通道模块只有一个 bank，行为和以前完全一样。
⚠ Applications 表里那几条，可能不是这只模块的全部。 这张表列的是基本 Application 描述符里的内容——最多 15 条， DataPath 那个 AppSel 下拉框给的也正是这些。
但 01h:175（Table 8-59）说的是：这 15 条是不是全部。 支持 Normalized Application Descriptors（NAD） 的模块， 把其余的 Application 放在 Page 1Ch 的若干个 bank 里， 最多能到 n×15 条。
规范里有一句几乎是照着这个毛病写的： 把这个字段读错的主机「甚至可能退化成只看到基本描述符里的前 15 条 Application」。而工具连这个字段都没读过—— 于是把 15 条当成全部摆出来，一个字都没说。 （这个字段在 CMIS 5.4 加宽成了整字节； 按 4 位读的话，16 个 bank 会变成 0，看着就像根本没有 NAD。）
现在：模块声明了 NAD，Applications 表下面会明确写出 有几个 bank、最多可能有多少条 Application、它们在 Page 1Ch， 并且直说这张表只是基本描述符。
有一点特意没有做：工具不读 Page 1Ch， 也不能去投运一条放在那里的 Application—— 选中那样一条还需要把它的 NAD 块号写进暂存控制集 （18h:128–143）。 假装能用比原来的沉默更糟，所以这里只把话说清楚， 不做「支持了」的样子。
⚠ 模块自带的页校验和，工具以前一个都没验过。 规范 8.3.11 写得很直白：页校验和是一个字节， 「可以用来验证该页上的只读静态数据是否有效」。 每个静态页都有：00h:222，以及 01h / 02h / 04h 的第 255 字节。 四个，一个都没读过。
这件事对这个工具尤其要紧：它本来就是用来调 会出问题的两线总线的。 一次读串了的声明数据，正是它存在的意义所在—— 而这时模块信息页上其它每一行都是假的。 模块递过来一个字节就能发现，工具却从来没问。
这里有三个不一样的范围，而 01h 是那个特例： 它从 130 开始，因为 「固件版本字节 128–129 被特意排除在页校验和之外， 以免固件一升级就得改内存映射」。
现在连接时会逐页核对：全部对得上，模块信息页会写 「N pages verified」；对不上就点名是哪一页， 并说明这一页的静态数据可能是读错了， 悬停能看到期望值、模块实际报的值，以及这一页校验的是哪段字节。
只核对模块确实有的页：01h / 02h 看内存模型是不是分页的，04h 看发射机是不是可调。 模块没有的页不会去核对——那种页读回来是什么全看模块， 据此报「数据损坏」是误报，比不报还糟。
内置演示模块以前这个字节全是 0， 等于每一只模块一验就是坏的—— 这恰恰就是从来没人去验的原因。 现在它们会算出真的校验和， 而 mock_fr4x2 的 01h 故意对不上， 好让「验不过」这条路也有东西走。
ℹ 「Media Interface: 1310 nm EML」不是模块自己报的波长。 模块信息页里那一行是 Table 8-40 的技术编码—— 它说的是一类技术、一个波段， 不是这一只模块实际发的波长。
01h:138–141（Table 8-46）才是模块自己声明的 标称波长和波长容差，工具此前没读过。 规范还特意写明：波长可编程的模块，这里报的是「实际值」—— 所以在可调模块上，技术编码和这个寄存器根本不是同一个说法。
这里有个很容易写错的地方：两个字段的刻度不一样—— 标称波长按 0.05 nm 计，容差按 0.005 nm 计。 两个用同一个系数，其中一个就会差十倍。
现在模块给了值就在「Media Interface」下面多一行 Nominal Wavelength，例如 1310 nm ±6.5 nm； 没给（两个字段为 0）就不出现这一行。
还有一条按规范办的：Table 8-46 说这两个字段是 给单波长模块定义的；多波长模块可以填（填一个波长、 或者整个范围的中心波长和总容差），但「解释方式没有唯一定义」。 所以工具会先判断这是不是单波长模块—— 靠的正是 11h:240–255 那份通道-波长映射（见上文）： 各通道映射到不止一个波长就说明不是。 是多波长的话，这一行会明确标出 「several wavelengths on this module」并在悬停里说明 规范没有唯一定义这个字段在这种模块上的含义—— 而不是把它当成「这只模块的波长」直接摆出来。
ℹ Aux 那几个读数，以前没有任何门限可比。 模块信息页会列出 Aux1–3——TEC 电流、激光器温度、第二路电源—— 但阈值页只有温度、Vcc、Tx 光功率、Tx 偏置、Rx 光功率， Aux 一个都没有。数字摆在那儿，却没有东西可以对照。
02h:144–175（Table 8-64）给的正是这几个监测量各自的 高低告警和高低警告（三个 Aux 各四档，外加一个 Custom 监测量）， 工具一个字节都没读过。
这里有个容易踩的点：这三个 Aux 根本不是同一种物理量—— Aux1 可能是TEC 电流（有符号百分比）、 Aux2 是激光器温度（1/256 °C）、 Aux3 是第二路电源电压（100 µV/LSB）； 究竟是哪一种由 01h:145 声明。 门限必须按各自监测量来解码， 否则把 TEC 电流的门限当温度读出来， 数值落在一个看着挺合理的范围里，单位却完全不对。
现在阈值页会按模块声明补上 Aux 各自的四档门限， 每行带上自己的名字和单位（如 Aux2 — Laser Temperature (°C)）。 模块没有某个 Aux 监测量、 或者四档门限全是 0（等于没给）时，那一行不出现—— 不拿一排 0 冒充门限。
⚠ 温度那个颜色，以前是工具自己定的，不是模块的。 监控页顶部那行温度，以前的规则是： 超过 60 °C 变黄、超过 70 °C 变红—— 这两个数字是直接写死在页面里的， 既不是模块的告警门限，也不是模块的额定范围。
可 01h:146–147（Table 8-50）说的正是 这个模块被允许工作的温度范围， 01h:150 说的是它需要的最低供电电压—— 工具都没读过。
后果很具体：一只额定到 85 °C 的工业级模块， 在 71 °C 时会被标成红色—— 而它离自己的上限还有整整 14 度； 反过来，一只只额定到 55 °C 的模块在 65 °C 时 还是绿色，其实早就超了。 这是整个界面上最先被看的那个数字， 而它的颜色跟模块无关。
现在颜色按模块自己的额定范围来，旁边直接写出 「rated −40…85 °C」；电压也会跟模块声明的最低电压比。 悬停会说明这是哪个寄存器给的。
有一点特意写清楚：那条黄色的「还差 5 °C 到上限」是工具自己加的余量， 模块给的是上限而不是告警级别—— 把工具自己的判断说成模块的，就又犯了同一个毛病， 所以提示语里明说了这 5 °C 是工具的。
模块两个温度字节都是 0 时，规范的含义是「未指定」， 这种情况下工具不上任何颜色，而不是替它编一个门限出来。
⚠ 「这条通道没卡住」——这句话工具以前没有资格说。 DataPath State 那一格悬停时，瞬态（DPInit / DPDeinit / DPTxTurnOn / DPTxTurnOff）写的是「正在状态之间迁移，没有卡住」。 可工具凭什么知道没卡住？
规范里有专门为此存在的字段：01h:144 和 01h:168（Table 8-48 / 8-56，只读、必需） 逐个给出这四个瞬态状态的最长时间， 原文写得很清楚——这些字段的用途就是让主机 「判断模块在这些状态里是不是出了问题，比如固件卡死」。 这些字节工具一个都没读过， 于是某条通道可以永远停在 DPInit，而提示语还在说它没事。
现在：瞬态提示会写明这个模块允许这个状态用多久、 以及已经用了多久；一旦超过模块自己声明的上限， 那一格会变成危险色并带一个「!」， 提示语改成「已经超过模块声明的时间，模块里可能有什么停住了」。 稳态（Activated / Deactivated / Initialized）没有上限可超—— 模块被放在那儿多久就是多久，不会被误报。
ℹ 翻页等待时间现在按模块声明来，不再一律等满 10 ms。 切页（写 0x7F）之后必须等 tBPC 才能读， 否则会读到上一页的内容——规范给的 tBPC 是 10 ms。 但那是最坏情况，不是每个模块的情况： 01h:169.3-0（MaxDurationBPC）声明这个模块 实际只需要 tBPC / 2i。 这个字节工具此前没读，于是每一次切页都按最坏情况等满 10 ms—— 而界面刷新一轮要切很多次页。
现在按模块声明来：声明 i=2 的模块只等 2.5 ms。 实测同样三轮完整刷新，从 0.44 秒降到 0.18 秒。 模块没声明（或声明 0）时仍然等满 10 ms， 连接过程中读到这个字节之前也一律按 10 ms 算—— 毕竟这段等待本身就发生在读到它之前。
ℹ 监控表的「Lane」列现在会写明这条媒体通道是哪个波长、哪根光纤。 表里列着媒体通道 1..N，每条一个光功率读数—— 可这一列看不出模块是并行的还是波分的。 这两者完全不是一回事：波分模块上好几条媒体通道共用一根光纤、 只靠波长区分；并行模块则每条通道各走各的光纤。 于是「第 3 条通道功率低」到底是某个波长弱了， 还是整根光纤有问题，界面上分辨不出来。
11h:240–255（Table 8-107）说的正是这个映射： 高半字节是媒体波长，低半字节是物理光纤 （TR1/RT1/TR2… 这套编号来自对应的硬件规范）。 这 16 个字节工具从来没读过。
现在模块给了映射的通道，Lane 那格下面会多一行小字， 例如 λ1 · TR1/RT1；悬停能看到完整的光纤名称。 两个方向波长相同时只写一次（双工光纤对本来就是这样）。
两个半字节都是 0 的含义是「未知或未定义」—— 这正是并行模块应该给的回答，所以这种模块下这行小字整个不出现， 而不是硬编一个「光纤 0」。
内置演示模块以前全都是 0，等于谁都没说， 所以就算读了也没东西可显示；现在 mock_fr4x2（2× 400G-FR4）会如实声明： 通道 1–4 是同一对光纤上的四个 CWDM 波长， 通道 5–8 走第二对——这正是原先那一列没法表达的情况。
⚠ 这份映射同样是按 bank 存的。 11h:240–255 这 16 个字节描述的是 本 bank 的 8 条媒体通道（先 Tx1–8、再 Rx1–8）， 所以 16 通道模块的第 9–16 条在下一个 bank 的同一批地址上。 工具以前只读一个 bank，也只解析 8 条通道， 于是第 9 条通道起没有任何映射—— 而「没有映射」在表里的画法，跟模块自己说 「未知或未定义」（0000b）是一模一样的。 波分模块明明报了波长，界面上却什么都不写。
现在逐 bank 读、按实际通道数解析。8 通道模块只有一个 bank， 行为和以前完全一样。
⚠ 工具以前一次读的字节数，超过了模块必须回答的数量。 规范 5.2.2.1 写得很直白：一次 READ 最多读 Nmax 个字节， 默认 Nmax = 8；只有模块声明支持整页读 （01h:251.1-0，Table 8-62，只读、必需）时才是 128。
这个字节工具从来没读过，而它一次要 64 字节 （诊断结果窗口）、32 字节（用户图案）、28 字节（附加 Application 描述符）； Raw 面板更是直接写着「Length must be 1–128」—— 那是模块说了支持整页读之后才成立的上限。 模块碰上超长 READ 怎么办是它自己的事： 地址回绕、中途 NAK 都可能，读回来的东西本来就不能当真。
现在：连接时先读这个字节，再做后面那些长读 （顺序反了的话，找上限的那几次读自己就已经越界了）； 超过上限的读会自动拆成若干次，对上层完全透明。 Raw 面板下方会写明这个模块一次答多少字节、 以及这次读是不是被拆开了。
内置演示模块以前来者不拒——要 64 就给 64， 所以这件事在演示里永远暴露不出来。现在它会像真模块一样拒绝， mock_fr4x2 声明不支持整页读（一次只答 8 字节）， 其余 profile 支持整页读，两条路径都跑得到。
⚠ 模块声明了的图案，下拉框里可能根本没有。 规范 Table 8-115 一共定义了 16 个 Pattern ID。 工具的寄存器层认得其中 15 个名字， 但网页自己另外存了一份图案名列表，而那份只排到 SSPRQ（ID 12）。 两份必须一致的列表分放两处——而用户看到的是短的那份。
结果：模块声明支持 Custom（14） 或 User Pattern（15） 时， 它们会被无声地从下拉框里滤掉； 某条 lane 本来就停在这两个图案上的话， 界面会显示一个光秃秃的数字并标注 not advertised——而模块明明声明了。
现在图案名由模块读取时一并下发，网页不再自己存一份， 这一类「两份列表迟早对不上」的问题从根上没有了。
ℹ User Pattern（ID 15）现在可以真的用了。 这个图案的内容由主机自己定义，放在 13h:224–255（Table 8-134）； 能放多长则写在 13h:140.3-0 （L = 2(n+1)，最短 2 字节、最长 32 字节）。 这两处工具此前都没读——也就是说就算选中了 User Pattern， 发出去的也是那段字节里本来碰巧是什么就是什么。
现在：只要有任一发生器或检测器声明了 ID 15， PRBS Generator 卡片下方就会出现用户图案输入框， 显示模块里当前的字节（十六进制），并写明是哪个寄存器、 以及模块最多收多少字节；随 Apply 一起下发。 输入不是完整的十六进制字节会被当场拒绝， 而不是把半个字节发下去。 比声明长度多写会被挡下并说明模块只收几字节。
没有任何角色声明 ID 15 的模块，这个框整个不出现—— 那段字节在这种模块上不是任何人能选中的图案。
内置演示模块里 mock_coherent 支持完整 32 字节， mock_coherent_zr 只收 4 字节—— 规范原文就写着「模块不一定支持完整的 32 字节长度」。
⚠ BER 和误码计数，以前没说是多长时间里的数。 两张表把数字摆出来，却从不说这些数覆盖多长的窗口； 而回答这个问题的两个寄存器都没被读。
13h:129（Table 8-112，只读、必需）说明模块 到底会不会门控一次测量，以及测量还在跑的时候 这些数会不会更新。工具其实早就把它解码了—— 从诊断面板写出来那天起——但解出来的结果没有任何地方用。
13h:177（Table 8-127）则完全没读过。其中 MeasurementTime 取值 000b 的含义是 「不门控，计数无限累加」——也就是说界面上那个 BER 是「自从上次有人翻动 ResetErrorInformation 以来的总账」， 不是任何一段确定时间里的误码率。 内置演示模块全都是这一种，而表格一个字都没提。
现在两张卡片顶部各写一行测量窗口：不门控就直说计数在无限累加、 这是总账不是速率；有门控就写出门控时长（如 60 秒）； 模块根本不支持门控时（13h:129.7-6） 就说明窗口取决于你让检测器跑了多久。 模块声明测量期间不做周期更新（13h:129.4）时 还会额外点出来——否则一个会自动刷新的面板， 看着就像数字在实时变。
内置演示模块现在三种写法都能看到： 默认那种不门控、mock_sr8 有 60 秒门控、 mock_fr4x2 既不门控、测量期间数字也不动。
⚠ 「参考时钟丢失」以前是句过头的话。 工具读了 14h:132.7（LossOfReferenceClockFlag）， 并在 PRBS 卡片顶部写「本模块的图案发生与检测在它恢复前都不可信」。
这句话模块从来没说过。13h:176 和 13h:178 （Table 8-127）逐字段说明四个引擎各自的时钟来源—— 模块内部时钟、参考时钟，还是从业务里恢复出来的时钟—— 而这两个字节工具从来没读过。 跑在内部时钟上的发生器、跑在恢复时钟上的检测器， 参考时钟丢了照样是原来那个样子。
这两个字段的编码还不一样：176 高半字节按 媒体 lane 数参考时钟，低半字节按主机 lane 数， 而且只有低半字节有「所有 lane 用参考时钟」这个取值。
现在：四个分区各自在标题下写明自己的时钟来源； 参考时钟真丢了的时候，那行字只点名真正用它的引擎， 四个都用就直接说「整页都用它」；一个都不用时， 它降为一条普通提示，说明这一页的图案不受影响。
内置演示模块以前这两个字节都是 0（发生器内部时钟、检测器恢复时钟）， 正好是那句警告全说错的那种配置；现在 mock_sr8 四个引擎全跑参考时钟，两种写法都能看到。
⚠ 四张 PRBS 表，模块不一定有那个引擎。 13h:131（Table 8-114，只读、必需）逐位声明 主机侧 / 媒体侧 的发生器与检测器各自存不存在， 以及每个位于自己 FEC 的哪一侧。 四个 Enable 字节（13h:144 / 152 / 160 / 168） 在规范里各自写着「Advertisement: 13h:131.x-y」， 指的就是这个字节——工具把它连同旁边的能力字节一起读了进来， 却直接丢掉。
一对位全为 0，表示模块压根没有这个引擎： 界面照样摆一张八行的表，勾了 Enable 也只是往一个没人读的字节里写数。
只有一位为 1 时，PreFEC / PostFEC 那一列只有一个合法值—— 另一侧没有引擎可跑。规范还特别写明： 没有内部 FEC 的模块，只存在 Post-FEC 发生器和 Pre-FEC 检测器， 也就是这两个框对这类模块本来就该是固定的。
现在：模块没有的引擎，那张表整块换成一行说明并注明是 13h:131 的哪两位决定的；只有一个位置的， FEC 那一列按模块实际所在的位置勾好并置灰，悬停写明原因； Apply 也会挡下「启动一个不存在的引擎」和 「把引擎放到 FEC 的另一侧」这两种写入。
内置演示模块以前把这个字节留成 0x00， 等于声明「本模块没有任何图案发生器和检测器」， 而界面把四张表全摆着——现在它们会如实声明： mock_sr8 是无内部 FEC 的模块（发生器只在 FEC 后、 检测器只在 FEC 前），mock_fr4x2 干脆只有主机侧 的一对引擎。
⚠ PRBS 表里那几列，模块不一定支持。 13h:141–142 是两个必备寄存器， 工具本来就把它们连同旁边的能力字节一起读了进来，却直接丢掉：
141 说明每个角色（主机/媒体 × 发生器/检测器） 到底有没有 DataInvert 和 SwapSymbolBits 这两个字节； 没有的话，勾了也不会有任何效果。
142 说明 Enable 和 Pattern 是不是按 lane 分： 位为 0 时，勾第 3 条 lane 的 Enable 实际上启动的是整个 Bank， 而 Pattern「一律用 lane 1 的」——也就是说第 2–8 行的下拉框 只是摆设。
现在这四列按模块声明置灰，悬停写明是哪个寄存器决定的； lane 1 那一行始终可用（模块确实有这个控制，只是作用范围是整个 Bank）。 内置演示模块之前把这两个字节留成 0，等于声明「全都不支持」， 而界面把四列全摆着——现在它们会如实声明， mock_fr4x2（那个“声明得比较少”的模块） 不支持符号位交换、主机检测器也不支持按 lane 启停。
⚠ PRBS 发生器也会失锁，以前界面上看不出来。 规范 Table 8-138（Page 14h 的锁存诊断标志）一共五个标志字节， 工具以前只读其中两个——检测器的失锁标志， 也就是 Checker 两张表里的 LOL 列。
没读的三个里，最要紧的是 14h:136–137 的 发生器失锁：发生器没锁上，就说明它并没有在发 控制寄存器里写着的那个图案。于是界面会显示某条 lane 正在发 PRBS31，而模块其实报告了失锁—— 对端测到的误码看起来像链路故障，实际上是源头就没发对。
另外两个：14h:132.7 是参考时钟丢失（整模块级， 丢了的话这一页上测什么都不作数）， 14h:134–135 是门控测量完成标志。
现在 Generator 两张表也有了 LOL 列，语义和 Checker 一致 （LOL 正在失锁、● 已锁定、 ●! 现在锁着但中途丢过——这些标志是读一次即清的）； 参考时钟丢失会在 PRBS Generator 卡片顶部单独标出。
ℹ Applications 表补上了「Media Lane Assign」一列。 规范 6.2.1.6 把 Application 描述符定义为五个字节， 第五个字节 MediaLaneAssignmentOptions 说明这个应用的实例 在媒体侧能落在哪几条 lane 上；它不跟前四个字节放在一起， 而是单独放在 01h:176–190。 工具以前只读前四个字节，所以每条描述符都少了五分之一—— 主机侧的起始 lane 位图有，媒体侧的没有。 对分路（breakout）应用来说，这一位图正是告诉你 每个实例占用哪几条媒体 lane 的唯一依据。
（平坦内存模块没有 01h 页，本来就不带这个字节，这一列会显示 —，不是读失败。）
⚠ 模块最多可以声明 15 个 Application，工具以前只读前 8 个。 AppSelCode 是 4 位，能取 1–15；而低页内存只放得下 8 条 Application 描述符，规范 8.4.17 把第 9–15 条放在 01h:223–250。 工具一直只读低页那 32 字节，于是第 9 个以后的应用完全不可见： 下拉框里没有、DataPath 分组不知道它占几条 lane， 更糟的是——它会被当成“模块从没声明过的码”， Apply 时回 ConfigRejectedInvalidAppSel， 拒绝一个模块其实支持的应用。
现在两段描述符会连起来读，终止符（HostInterfaceID = FFh）落在哪里就读到哪里； 声明 8 个及以下的模块行为完全不变。
⚠ Signal Integrity 表里的数值，模块不一定在用。 这张表读的是 Page 10h 的暂存区——你要求的值。 而规范 Table 8-104 / 8-105 说得很清楚： DPConfigLane 里的 ExplicitControl 位置 1 时， 生效的值才来自暂存区；清 0 时， 「这些值由模块根据所选 Application 自行决定」。
本工具写的一直是 0（一条数据通道、从 lane 1 起、SI 由 Application 决定）， 所以每一次 Apply 之后，真正生效的都不是表里显示的数字。 模块把自己实际配置的值发布在 11h:214–234， 紧挨着工具早就在读的 Active AppSel——但这一段从来没被读过， 表格下方却写着“Apply 会把这一套一起下发”。
现在两边不一致的格子会在数值下面标出 in force N（模块实际在用的值）， 悬停说明它来自 Active Control Set 以及 ExplicitControl 的含义； 表格下方那句话也改了。
ℹ 信号完整性设置也会被校验了。 模块在 01h:153–154 里声明了三个上限—— Tx 输入均衡最大值、Rx 输出均衡的前/后游标各自的最大值—— 以及它到底有哪几个 Rx 输出幅度码。 要得比模块声明的多，就是 ConfigRejectedInvalidSI（5h）。
以前演示模块根本不看暂存区的信号完整性那一半， Apply 会把模块从没说过自己能做到的值一起提交； 而且八个演示模块把三个上限全都声明成了字段能装下的最大值 （7、7、7，四个幅度码全有）， 所以从来没有一个“有真实限制”的模块可以用来对照—— 前后游标两个上限相等，意味着把 01h:154 的两个半字节读反了也看不出来。
现在 mock_fr4x2（本来就是那个“声明得比较少”的演示模块） 声明的是：Tx 均衡最大 3、前游标最大 5、后游标最大 2、 只有 0 和 1 两个幅度码。 Signal Integrity 表里超出上限的数值会标红， 悬停写明模块声明的上限，以及这样 Apply 会得到哪个拒绝码。
ℹ 内置演示模块现在会按这些规则真的拒绝。 以前它只校验 AppSel 码有没有被声明过，别的一律放行， 所以 4h、7h 这些理由在界面上从来没出现过。 现在它按 CMIS 6.2.4.3 的主机规则校验：应用必须整段落在 它声明的起始 lane 上（否则 4h），Apply 必须覆盖整条 DataPath （否则 7h，热重配 ApplyImmediate 除外）。
连带修正了一处演示模块自相矛盾的地方：双 4-lane 端口的 mock_fr4x2 声明 App 1 只能从 lane 1 起、App 2 只能从 lane 5 起，开机默认却是八条 lane 全跑 App 1——这是它自己的 声明所禁止的配置。现在默认是 lane 1–4 跑 App 1、lane 5–8 跑 App 2。
ℹ 连续点两次 Apply：按规范，上一次还在 ConfigInProgress 时到达的新命令会被模块静默丢弃（不给任何反馈）。 工具现在会等 ConfigStatus 出结果再下结论，不会把“还在处理中”报成“已应用”。

⚠ 以前这种情况下左上角会一直写着 Connected — mock_dr8…，而你点什么按钮都报错， 错误还是一个一个弹出来的。
现在工具会直接把状态改回 Disconnected、回到 Module Info 页、 弹一条“服务端已没有连接的模块，请重新连接”。重新点 Connect 即可继续，不需要刷新页面。

Module Restarts —— 模块自己重启过的记录

上面讲的是单条通道。模块整体也有一个对应的标志： ModuleStateChangedFlag（Lower 0x08[0]，CMIS 6.3.2）。 模块每次进入新的 Module State 都会置位——复位、掉电又上电、 固件切换都算。

⚠ 它同样是闩锁、读清的。一个模块在两次刷新之间重启完成， 前后两帧看到的都是 ModuleReady，温度电压也正常—— 没有任何一栏会告诉你它刚刚重启过。 现在 Module Info 里的 Module Restarts 一行会保留 ●! Restarted since last clear， 顶部摘要栏同时出现 ↺ Restarted。 与 Lane Flags 的历史共用同一个 Clear flag history 按钮。
ℹ 你自己点 Software Reset 也会点亮它，这是正常的。 它不算告警——顶栏的 ⚠ Alarm Active 只代表有读数超出阀值，不会因为重启而亮。

PRBS 检测器中途失锁

Diagnostics 里的 PRBS 表格同样适用这条规则。检测器的 LOL（Loss of Lock）位在 14h:0x8A–0x8B（Table 8-138）， 同样是 RO/COR——门限、读清。

⚠ 跑一个长时间的 BER 测试，中途失锁正是你要找的东西， 而下一次刷新它已经重新锁上，表里看起来一切正常。
现在失过锁的通道会在 Lock 列保留 ●! 标记。看到它就说明这条通道的 BER 结果不可信——计数器在失锁期间是无意义的，应该清一次重跑。
ℹ 排查间歇性链路时的用法：连上模块、点一次 Clear flag history， 然后让它跑着。回来时看哪些通道带 ●! ——那就是这段时间里出过问题的通道， 哪怕它现在一切正常。DP Changed 那一列尤其要看：光功率抖动可能只是脏接头， 而数据通道真的重建过，说明链路断过。

Squelch Method —— 这一项未必轮得到主机选

01h:155[5:4]（Table 8-51）说的是谁来决定 Tx 输出怎么静音：00b 不支持静音； 01b 模块靠降 OMA 静音；10b 模块靠 降 Pav 静音；只有 11b 才是“主机选”。 主机用来选的位是 Lower 0x1A[5]。

⚠ 模块自己定了方法时，那个位不算数。 旧版本把 0x1A[5] 直接当作“当前方法”显示， 于是在一个声明“我降 OMA”的模块上， 只要那个位被置上，面板就显示 Pav—— 恰好和模块实际做的相反。现在面板显示的是 实际生效的方法，并在模块定方法时标注 “fixed by the module”；接口也不再接受这个写入， 而是告诉你模块定的是哪一种。

Bank Broadcast —— 开了之后“写一个 Bank”就不存在了

Lower 0x1A[7] BankBroadcastEnable（Table 8-11，广告位 01h:156[7]）。置 1 之后，向任何一个 Bank 的控制寄存器写入，都会被模块 当作对所有 Bank 的同时写入执行。

⚠ 这会把逐 Bank 不同的配置静静拍平。 多 Bank 模块上，工具本来是按 Bank 分别写入 不同的掩码字节的；开了广播之后， 每一次写都落到全部 Bank，最后一个 Bank 的值会盖掉前面全部。例子：在 24 通道 模块上请求关掉 lane 1 / 10 / 19，开广播后实际 关掉的是 lane 3 / 11 / 19——而接口还回了成功。
现在遇到这种情况工具会直接拒绝并 告诉你是哪一项逐 Bank 不一致，而不是写下去 再报成功；原来的配置不会被动。 这项检查覆盖每一个按 Bank 写入的地方：DataPath、Squelch、 媒体通道切换、Loopback、PRBS、激光调谐（Page 12h） 和采集计数器清零（Page 60h）。 所有 Bank 取同一个值时照常写入（那本来 就是广播能表达的）。
ℹ 这个位在所有模块上都是可读写的， 但只有广告了才真的生效；未广告的 模块上写它只会让界面看起来“开了”。 因此工具对未广告的模块拒绝这个写入。 内置模拟模块里只有 mock_24lane（3 个 Bank） 广告它——单 Bank 模块根本无处可广播。

10.4 BER Results（误码率）

向 14h/0x80 写入 Selector = 0x01 选择 BER F16 诊断。Host BER 在 14h/0xC0，Media BER 在 14h/0xD0，每通道 2 字节。

F16 解码公式（CMIS 5.4 十进制浮点）：BER = mantissa × 10^(exp − 24)，其中 bits[15:11]=exp, bits[10:0]=mantissa。

信号质量典型 pre-FEC BER
接近底噪（优良）< 1e-9 ~ 1e-8
正常工作1e-8 ~ 1e-4
边缘1e-4 ~ 1e-3
劣化> 1e-3
⚠ 表格里显示 0 的含义是"模块报告零错误计数"，不是测到的 BER 下限。 上表没有 0 这一档是有意的：真实的可达下限取决于该次统计门累积了多少比特， 模块并不告诉你这个数。请不要把 0 当作实测值写进测试报告—— 需要给出量化结果时，应根据码率与统计时长自行算出置信下限。 鼠标悬停在 0 上也有同样的说明。显示 — 表示该 lane 没有有效读数。

10.5 SNR Results（信噪比）

向 14h/0x80 写入 Selector = 0x06 选择 SNR 诊断。Host SNR 在 14h/0xD0，Media SNR 在 14h/0xF0，每通道 2 字节小端 u16，单位 1/256 dB。

典型 400G/800G 链路 SNR 范围：PAM4 DSP 输出约 15–22 dB，越高越好。低于 13 dB 通常意味着链路劣化。

ℹ BER / SNR 读取无需 PRBS 使能，直接反映当前链路质量。若同时开启 PRBS 发生/检测，结果对应 PRBS 码流质量。

10.7 Laser Tuning（激光调谐）— 仅限可调谐模块

11. Raw Registers — 寄存器直读写

11.1 读取寄存器

  1. 填写 Page（如 0x00、0x11）
  2. 填写 Address（起始地址，如 0x80）
  3. 填写 Length（读取字节数，1–128）
  4. 点击 Read

结果以十六进制 Dump 格式显示：

0x80: A1 B2 C3 D4 E5 F6 01 02  ........
0x88: 03 04 05 06 07 08 09 0A  ........

格式：地址: 十六进制字节  ASCII（不可打印字符显示为 .）

11.2 写入寄存器

  1. 填写 Page 和 Address
  2. 在 Write Data 输入框填入字节（空格分隔十六进制，如 1E 50 00）
  3. 点击 Write
ℹ 地址 ≥ 0x80 为上页寄存器，工具自动切页；地址 < 0x80 为下页，忽略 Page 字段。
⚠ 本页对写入不设任何护栏，这是有意的。其它标签页只暴露安全的操作，这里能写模块的任意字节—— 它存在的理由正是让你做界面没有提供的事。代价是：在跑着业务的模块上，一次误写就可能断流。
几个后果最直接的地址见下表（工具不会拦，模块会照做）。
地址写下去会发生什么
Lower 0x1A bit 3软复位——模块重启，所有数据通道重新初始化，链路中断数秒
10h:0x8F = FFApplyDataPathInit——按当前暂存配置重新初始化数据通道，相应通道断流
10h:0x82关闭对应通道的发送端，该通道立即无光
Lower 0x7E / 0x7F直接改动 Bank / Page 选择。工具会察觉并作废自己的缓存， 所以后续读取仍然正确；但如果你在中途改页，紧接着的那次读取读到的是你选的页，不是你以为的页
ℹ 会被拒绝的只有三种：跨页越界（起始地址 + 长度超过 0xFF）；从 0x7F 以下一直写过 0x7F（中途会改掉页选择）；以及 Page 9Fh 上超过 8 字节、包含字节 129 的写入（见下）。 只读与保留字节可以写，但模块会忽略或钳位——那时出现红色回读提示是正常的（见上一节）。

超过 8 字节的写入会分几次完成

规范 5.2.2.2 规定一次 WRITE 最多 8 字节，所以更长的写入会拆成若干次、每次最多 8 字节，结果区会写明 as N WRITEs of up to 8 bytes each (5.2.2.2)。这样写入的一段寄存器不是一次整体写入的（规范 5.2.5.2）。Page 9Fh 例外：写到 9Fh:129 就会发出 CDB 命令（规范 7.2.3），所以超过 8 字节又包含 129 的写入不会替你拆，而是提示你先写其余部分、最后写含 129 的那段。

写完之后工具会回读比对——看懂那条红色提示

写操作返回成功只代表 I2C 传输完成，不代表模块真的接受了这个值。所以工具写完会立刻 把同样长度的字节读回来，与你写入的逐字节比较，并把读回的内容显示在下方 hex 转储区：

提示含义
绿色 Written and verified …（3 秒） 读回值与写入值完全一致
红色 Write completed but the module reports different values（8 秒） 这不是工具故障。传输成功了，但模块把值改掉或忽略了—— 最常见的原因是写到了只读或保留字节，其次是模块把超范围的值钳位到了合法区间。 写只读寄存器时出现这条提示是正常现象

另有三种情况会在写出去之前就被拒绝，此时模块没有收到任何字节：

  • 十六进制无效：Write Data 里没有一个能解析的字节，提示 Invalid hex data
  • 越过页尾：起始地址加字节数超过 0x100，提示 Write would cross end of page
  • 跨过 0x7F 的多字节写：一次写入若从 0x7F 之前开始、越过它继续写，会在传输中途 改掉页选择寄存器，剩余字节将落到另一页上。工具直接拒绝并要求你拆成两次写
✕ 警告：直接写寄存器可能影响模块正常工作，请在熟悉 CMIS 规范的前提下操作。 本页的写入没有确认对话框，点 Write 立即执行。

13. 常见问题排查

Q1双击 EXE 后控制台窗口一闪而过
原因：程序启动异常。端口被占用已不再是原因—— 被别的程序占用时会换一个临时端口启动并弹窗让你选端口（见第 4 章「本机端口」）， 被本工具自己占用时会直接打开已在运行的那一个。
解决：从命令行（cmd）里运行 EXE，窗口就不会关闭， 最后几行会写明失败原因。
不要试图用"以管理员身份运行"解决：监听 127.0.0.1 上的端口本来就不需要管理员权限。
Q2浏览器显示"无法访问此网站"
原因：控制台窗口已被关闭，服务器停止运行。
解决：重新双击 EXE 启动，保持控制台窗口开启。
Q3Backend 下拉菜单只显示 mock_coherent/dr8/sr8/fr4x2，没有 ch341/ch347/ftdi
可能原因及对应解决方法：
  • USB 适配器未插入 → 插入适配器后点击 ↻ Refresh Backends 重新扫描。
  • 驱动未安装 → 参考第 3 节《USB 驱动安装指南》，安装对应型号的 WCH 驱动后再刷新。
  • 驱动已安装但仍不显示 → 打开设备管理器，检查适配器图标是否有黄色感叹号；如有，请重新运行驱动安装程序。尝试拔出适配器并重新插入，再点击 ↻ Refresh Backends。
  • CH347 特有问题：设备管理器正常但工具显示 unavailable → 串口驱动（CH347SER.EXE）只让系统识别设备，但 I2C 通信需要 CH347DLL.dll，该文件可能未随驱动自动安装。从 WCH 官网下载 CH347EVT 开发资料包，找到 CH347DLL.dll，复制到 EXE 同目录，重启工具即可。详见第 3 节。
Q4点击 Connect 提示 "Connect failed"
原因：Backend / Bus / I2C 地址与实际设备不匹配，或模块未正确连接。
解决：确认 I2C 地址（光模块通常为 0x50）、Bus 编号正确；检查模块与适配器的物理连接。
Q5Monitoring 功率显示 −inf dBm 或全为 0
原因：模块处于低功耗状态，或无光纤输入（Rx 功率为 0 时 dBm = −∞）。
解决：检查 Module Info 中 Module State 是否为 ModuleReady；检查光纤连接。
Q6Mock 模式的数据是真实的吗？
不是。Mock 模式返回按 CMIS 5.4 规范构造的模拟数据（含动态波动和状态机响应），仅用于软件界面验证和培训演示，不反映真实模块状态。当前提供 12 种 profile：mock_coherent（800GBASE-LR1 数据中心 coherent lite）、mock_coherent_zr（C-band 可调谐 ZR 类）、mock_dr8、mock_sr8、mock_fr4x2、两块 1.6T 模块，mock_24lane（24 通道 / 三 Bank），mock_zr16（16 通道可调谐 / 两 Bank），mock_fewmon（只实现部分监控项），以及 mock_aoc（400G 有源光缆，媒介不可分离）。
Q7为什么 mock_dr8/sr8/fr4x2 的 Laser Tuning 卡片显示"非可调谐模块"？
原因：这些 profile 模拟的是固定波长激光器（EML / VCSEL），Media Interface Technology ≠ C-band/L-band tunable。
正常现象。只有 mock_coherent_zr（Media Interface Tech = 0x10 C-band tunable）支持 Laser Tuning 功能。真实模块的 Page 04h GridSupported 寄存器若为 0，说明不支持调谐。
Q8mock_fr4x2 的 Host/Media Lanes 为什么显示 8 而不是 4？
2× 400G-FR4 模块通过 CMIS 广告两个独立的 400GBASE-FR4 应用（AppSel#1 占用 host 通道 1-4，AppSel#2 占用 host 通道 5-8），两个应用并发运行得到 800G 总容量。
GUI 会遍历所有 Application Descriptors 并计算最大并发通道数（非重叠应用相加）。Host Lanes 后括号中显示了每个 AppSel 的明细。
Q9Apply 之后偶尔报 read failed / write failed / NACK
原因:写入之后,模块在规范允许的时间内(一般 10 ms,Page 03h 为 80 ms,Table 10-4)可以暂时不应答。工具会在这段时间里自动重试,所以正常情况下不会看到这类报错。
仍然出现,说明模块超过了规范允许的时间还不应答,或者连线 / 适配器有问题:检查 I2C 连线与上拉、换一个适配器或降低速率再试;同一操作反复出现,记下操作步骤联系模块厂商。

12. CMIS 5.4 扩展功能

CMIS 5.4 新增的几个可选页不设单独标签页，按用途放进对应的功能标签， 卡片标题后带 5.4 徽标（与字段名后的标记同一个），5.4 新增内容一望可辨：

功能所在标签页寄存器页

这些页是否存在由模块在 01h:173–174 / 01h:252[5] 广告决定——没有广告的页本工具不会去读： 未实现的页不保证返回有意义的内容，读了再渲染等于把总线上的残留值变成"每通道读数"。 没广告的页对应的卡片直接不出现；5.3 模块以及不实现这些页的 5.4 模块， Module Info 里的 CMIS 5.4 Optional Pages 卡片会明确写"没有广告任何可选页"，这是正常的。

12.1 Lane Polarity Status（60h:128–129，DataPath Config 标签页）

模块当前实际生效的通道极性。它与 Module Info 里的 Default Polarity （01h:171–172）可以合法地不一致：后者只广告上电时的极性， 而支持可编程极性的模块把实时状态放在 60h。两处不同不是故障。

12.2 Acquisition Counters（61h:128–191，Diagnostics 标签页）

四类饱和计数器：通道 Tx/Rx、数据通道 Tx/Rx。统计的是数据通道投入使用后 接收侧重新锁定信号的次数，模块在 DPInit 时自动清零。

ℹ 这是本页最有诊断价值的一项：链路状态看起来一切正常、误码率也不高， 但该计数持续增长，说明接收端在反复失锁重锁——这种间歇性问题在瞬时读数里看不出来。

填入通道号（如 1,3,9）点复位所选通道计数即可清零，写的是 60h:192–193。

⚠ 只提供通道计数器的复位，不提供数据通道（DP）计数器的复位。 规范 Table 8-189 把媒体侧与主机侧 DP 复位寄存器都印成了字节 195， 因此 194 号究竟属于哪一个无法从文档判定。复位命令写错地址会清掉没人要求清的计数器， 所以本工具不猜——需要时请用 Raw Registers 自行确认后写入。

12.3 Per-Lane Output Power Thresholds（62h:128–191，Monitoring 标签页）

按媒体通道给出的绝对发射功率门限（S16，0.01 dBm），每通道一组四个值。 启用了相对门限（见 §10.7）的通道以这里的值为准， Page 02h 的模块级门限对它不再适用。

12.4 Media Lane Switching（6Dh:136–191，DataPath Config 标签页）

把内部媒体通道重定向到不同的外部通道。填入目标顺序（如 2,1,4,3,5,6,7,8 表示内部 1→外部 2、内部 2→外部 1，依此类推），先暂存，确认无误再提交。

  • 映射必须是通道的一个置换——每条外部通道恰好被用一次 （按组校验，见下方说明）。 不是置换的映射本工具直接拒绝下发，因为模块校验后也会拒绝， 而那时你已经被告知"写入成功"了
  • 当前映射若不是置换，表格下方会以红色标出，本工具不会替你排序修正—— 那正是需要你看见的信息
  • 「已下发」是暂存值（6Dh:136–143），「当前生效」是交换机实际在做的 （6Dh:184–191，只读）。勾选 Enable 本身不会提交， 两列不一致表示提交还没做或被拒绝
  • 「上次提交结果」逐通道显示模块回报的状态：成功 / 进行中 / 四种拒绝原因
⚠ 提交会中断业务：重定向发生变化的通道会断流（未变化的通道按规范不受影响）。 点提交前会弹确认框。
⚠ 超过 8 条通道的模块，这个面板以前只管前 8 条，而且没说。 Page 6Dh 是按 bank 分组的，规范原文说每个 bank 提供的是 一组 8 条通道之内的交换能力——表 8-196 里所有字段的取值都是 {1, …, 8}，所以目标通道永远是本组内的通道， 交换不能跨组。
以前工具只读第一组，下发时把目标列表截断到 8 个， 使能和提交也只写第一组——然后回报成功。 也就是说：在 16 通道模块上填 16 个目标， 后 8 条通道根本没被写、没被使能、也没被提交， 而面板上写着「已使能、已提交」。这是界面在替模块说一件它没做的事。
另外，寄存器里的目标值以前是原样打印的：第二组里的 3 指的是本组的第 3 条，也就是第 11 条通道， 界面上却写成「3」。
现在：表格列出全部通道并标出所属组，目标列显示绝对通道号 （原始寄存器值放在悬停提示里）；置换校验逐组做， 所以两组各自用 1–8 是合法的；暂存、使能、提交都写到每一组； 目标个数超过模块通道数会被直接拒绝，不再默默丢掉多出来的部分。 某几组使能、某几组没使能时，表格下方会明确写出是哪几组。
8 通道模块只有一组，行为和以前完全一样。
